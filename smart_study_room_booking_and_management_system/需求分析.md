## 1. 问题（Problem Statement）

随着高校学生自习需求的持续增长，传统自习室管理方式暴露出以下突出问题：

1. **座位资源信息不透明**：学生无法提前获知自习室座位占用情况，需要到现场"找座"，高峰时段常出现"空占座、真人无座"的资源浪费现象。
2. **预约流程缺失**：缺乏统一的线上预约渠道，座位使用靠排队、占座等无序方式分配，易引发同学间的矛盾。
3. **违约行为缺乏约束**：预约后不到场、签退后滞留、长时间占座离开等行为没有系统化的记录与惩戒机制，座位周转率低。
4. **管理手段低效**：管理员依赖人工巡查登记座位使用情况，工作量大、时效性差，难以实时掌握各自习室的运行状态。
5. **缺乏数据支撑决策**：座位利用率、违约率、高峰时段分布等数据未被采集与分析，学校无法依据数据优化自习室开放策略与资源配置。
6. **投诉反馈渠道不畅**：学生对设施故障、占座行为等的投诉缺乏统一的提交与处理闭环，管理方也缺少对管理人员服务质量的评价机制。

**一句话概括**：本系统旨在通过线上化、智能化的预约与管理手段，解决高校自习室"座位资源分配不均、违约无约束、管理低效、决策无数据"的问题。

## 2. 业务目标（Business Objectives）

本系统面向高校自习室场景，构建覆盖"预约—签到—使用—签退—评价"全流程的智慧化管理平台，并辅以违约治理、投诉闭环与数据可视化分析。

| 编号 | 业务目标 | 说明 | 优先级 |
|------|----------|------|--------|
| BO-1 | 实现自习室座位资源的统一线上管理 | 管理员可维护自习室与座位的属性信息（位置、类型、设施、状态等），实现资源数字化 | 高 |
| BO-2 | 提供便捷的预约与取消预约服务 | 学生可按日期、时段、自习室查询并预约座位，支持在规定时间内取消预约 | 高 |
| BO-3 | 建立签到/签退与自动违约机制 | 通过签到签退核验实际使用，系统自动记录超时未签到、未签退等违约行为 | 高 |
| BO-4 | 提供多维度查询能力 | 支持预约记录、座位实时状态、个人违规记录等查询 | 高 |
| BO-5 | 支持管理员实时座位管理与手动违约登记 | 管理员可查看实时座位使用情况、查看座位使用预约记录、手动登记现场违规行为 | 高 |
| BO-6 | 建立用户管理与信用治理体系 | 用户信息管理、评价管理、投诉管理与反馈、黑名单管理（多次违约用户限制预约） | 中 |
| BO-7 | 提供数据分析与可视化 | 柱状图、折线图等多形式统计展示（利用率、违约趋势、高峰时段等），每 10 秒自动刷新 | 中 |
| BO-8 | 提升座位资源利用率与管理效率 | 通过上述机制减少空占、提高周转率、降低人工管理成本 | 高 |

## 3. 成功指标（Success Metrics）

| 指标 | 度量方式 | 目标值（示例） |
|------|----------|----------------|
| 座位资源利用率 | 已使用座位时长 / 可用座位总时长 | 较上线前提升 20% 以上 |
| 预约履约率 | 正常签到完成的预约数 / 总预约数 | ≥ 90% |
| 违约率下降 | 违约记录数 / 预约总数 | 系统运行一个学期后下降 30% |
| 高峰时段"到场无座"投诉量 | 投诉记录中相关类别数量 | 显著下降 |
| 管理人工成本 | 管理员日均巡查登记耗时 | 降低 50% 以上 |
| 数据刷新时效 | 统计页面自动刷新间隔 | 10 秒 |
| 用户满意度 | 学生对自习室管理服务的评价得分 | ≥ 4.0 / 5.0 |

## 6. 系统范围（System Scope）

### 6.1 范围内（In Scope）

1. **自习室（座位）资源管理**：自习室信息、座位属性（编号、类型、电源/隔间等设施、状态：可用/维护中/停用）的增删改查。
2. **预约管理**：用户端与管理员端的预约、取消预约；时段与容量冲突校验。
3. **签到与签退**：预约时段内签到核验、使用结束签退；超时未签到、提前/超时离开等自动违约判定与记录。
4. **查询功能**：预约查询、座位实时状态查询、违规记录查询、座位使用预约记录查询。
5. **管理员实时管理**：实时座位状态大屏/列表、手动违约登记。
6. **用户管理**：用户信息管理、评价管理（对管理服务的评价）。
7. **投诉管理**：用户投诉提交、管理员处理与反馈信息推送。
8. **黑名单管理**：违约累计达到阈值的用户自动/手动加入黑名单，限制其预约权限。
9. **数据分析**：柱状图、折线图、统计数据展示（利用率、违约趋势、时段分布等），每 10 秒自动刷新。

### 6.3 非目标（Out of Scope / Non-Goals）

以下内容明确不在本期系统范围内：

1. **硬件集成**：不接入门禁闸机、智能座位传感器、摄像头等物联网设备，签到签退通过系统操作完成（不做物理身份核验）。
2. **支付功能**：不提供在线付费预约、押金收取或退款功能。
3. **统一身份认证集成**：暂不对接学校统一身份认证（CAS/OAuth）系统，采用本系统独立账号体系。
4. **多校区/跨校推广**：本期仅面向单一校区的一处或多处自习室，不考虑多校区统一平台。
5. **移动端原生 App**：不开发原生 App，仅提供 Web 端（自适应页面）。
6. **智能推荐与预测**：不提供基于 AI 的座位推荐、人流预测等智能算法功能（数据分析仅限统计展示）。
7. **消息推送渠道集成**：不对接短信/微信公众号等外部通知渠道，通知仅在系统内展示。
8. **设施运维管理**：不管理空调、照明、消防等楼宇设备的运维工单。

## 2. 优先级

### 2.1 优先级口径

按 Kano 模型把需求分为基本需求、期望性需求、兴奋性需求，并叠加"课程必做范围"这一外部约束：

| 优先级 | 含义 | 排序处理 |
|---|---|---|
| **基本** | 不满足则系统无法完成核心业务闭环，用户会直接无法使用 | 必须在本期完成，全部列入需求清单 |
| **期望** | 做得越好用户越满意，做得差会明显降低满意度 | 本期完成，若进度紧张可先简化为可接受的最低实现 |
| **兴奋** | 用户未明确期待、出现会带来惊喜，缺失不影响正常使用 | 本期不承诺，列入后续迭代 |

**必做范围判定**：任务原文的 7 条核心功能全部列入"基本"或"期望"，不得裁剪；AI 候选功能一律不高于"期望"，且不得与原文功能争夺本期资源。每个 Basic/期望项都对应一条"验收底线"：功能有数据留痕、状态流转正确、权限可拒绝。

### 6.4 UC-04 实时座位监控与手动违约登记

| 成功后的结果 | 新增 1 条手动违约记录（类型=手动，含原因与操作人）；预约单"已签到 → 已违约"；座位"使用中 → 空闲"；学生收到违约通知；违约计数 +1 |

### 6.5 UC-05 投诉提交与处理反馈

| 预期使用频率/触发规律 | **待确认。** 口径：投诉量相对预约量明显更低，量级受违约判定准确率和现场管理质量影响，需上线后统计。处理时限 3 个工作日为 AI 候选（KQ-04）。 |

### 6.6 UC-06 违约累计与黑名单加入/解除

| 项目 | 内容 |
|---|---|
| 编号与名称 | UC-06 违约累计、黑名单加入与解除 |
| 参与者 | 系统定时任务（自动加入/期满解除）；管理员（查看、申诉处理、提前解除）；学生（接收通知、申诉） |

| 主流程 | 1. 违约记录写入后，系统按 BR-07 的统计窗口重新计算该用户违约累计次数。<br>2. 若达到阈值且用户当前不在黑名单内：创建黑名单记录（起始时间、结束时间按 BR-07 计算），用户"正常 → 黑名单"。<br>3. 系统向用户推送加入黑名单通知（含原因、解除日期）。<br>4. 黑名单期内，用户任何预约提交均在 UC-01 第 4 步被拒绝（UC-12）。<br>5. 定时任务在结束时间到达后自动解除，用户"黑名单 → 正常"，推送解除通知。<br>6. 若存在申诉且管理员判定成立：管理员提前解除并记录理由，推送解除通知。 |

| 异常流程 | 2a. 定时任务重复执行：以"该用户是否已有生效中的黑名单记录"为幂等条件，不重复创建。<br>2b. 用户在系统当前设定的阈值与确认后的阈值不同时（规则定稿前）：以数据库中实际生效的规则参数为准，不硬编码；参数调整需留痕。<br>5a. 解除任务漏跑：用户的限制期实际已过但状态仍为黑名单，系统按当前时间判断时以"当前时间是否晚于结束时间"为准，查询与预约校验均以时间为准，不依赖状态字段被及时刷新（兜底规则，需在规则章节确认）。<br>6a. 管理员无权限解除：拒绝并记录日志。<br>6b. 解除时黑名单记录不存在或已解除：拒绝并提示。<br>2b. 用户查询到黑名单后联系管理员要求解释，管理员可查看该用户的违约明细（FR-16）。 |
| 成功后的结果 | 加入：新增 1 条生效中的黑名单记录；用户预约资格受限；通知已推送。<br>解除：黑名单记录状态更新为"已解除/到期解除"；用户恢复预约资格；通知已推送；解除原因已留痕。 |
| 失败后的结果 | 加入失败：用户状态保持"正常"，不产生黑名单记录，违约计数不变。<br>解除失败：黑名单保持生效，不产生解除记录，不推送通知。 |
| 关联规则 | BR-07（阈值与统计窗口，候选 30 天 3 次、限制 7 天）、BR-06（手动/自动违约统一计数）、BR-15（通知）、BR-16（申诉流程，候选）；状态转换 ST-13（加入）、ST-14（解除）；权限：加入以系统判定为主，管理员可查看、复核、处理申诉、提前解除及人工加入/移出（P-10，均须留痕） |
| 验收标准 | ① 用户在统计窗口内第 3 次违约后，状态变为黑名单且预约被拒绝。<br>② 黑名单用户在期间提交预约，返回"限制预约"及解除日期。<br>③ 到期后自动解除，用户可以正常预约。<br>④ 管理员提前解除后，解除记录中含理由，且用户可立即预约。<br>⑤ 定时任务重复运行不产生重复黑名单记录。<br>⑥ 黑名单期内用户已有的未来预约如何处理（是否取消）与确认后的规则一致（KQ-09）。 |
| 预期使用频率/触发规律 | **待确认。** 口径：加入黑名单次数 ≈ 违约次数 ÷ 阈值；定时任务固定周期触发（周期**待确认**）。阈值为 AI 候选，需教学模拟确认（KQ-02）。 |

# 规则与权限

> 应能够查到的内容：允许、禁止及计算规则，角色及对象范围限制
> 推荐表示形式：规则表、权限矩阵，必要的决策表
> 关键内容要求：权限矩阵同时考虑角色和对象范围。例如，"教师可查看提交"还需说明是所授课程的提交，还是所有课程的提交。

## 1. 角色定义（Roles）

| 角色 | 说明 |
|------|------|
| **学生（普通用户，STU）** | 系统的核心使用者，执行预约、签到签退、查询、投诉、评价等操作 |
| **管理员（ADM）** | 自习室日常运营者，维护资源、实时管理座位、登记违约、处理投诉与反馈、管理黑名单、查看统计分析 |
| **运维（OPS）** | 系统建设与维护方，监控系统运行状态与资源占用，不参与日常业务数据的管理 |

## 2. 允许规则（Permission Rules）

| 编号 | 规则内容 |
|------|----------|
| P-1 | 学生**最多可同时持有 2 个有效预约**（含已预约未开始、已签到使用中），超出则拒绝新预约 |
| P-2 | 学生**早上可以预约当天下午及未来日期的座位**（即预约开始时间不得早于当前时间，且可提前预约未来 7 天内的时段） |
| P-3 | 学生**只能查看和操作本人**的预约、签到签退、违规记录、投诉与评价数据 |
| P-4 | 学生可在**预约时段开始前 ≥ 30 分钟**主动取消预约，取消后座位立即释放，不计违约 |
| P-5 | 学生可在**预约开始后 15 分钟内**完成签到；在预约结束前完成签退 |
| P-6 | 学生可对**已完成的预约**提交一次评价；可对管理服务提交投诉并查看投诉反馈信息 |
| P-7 | 管理员可对**全部自习室与座位**的信息（属性、状态）进行新增、修改、停用/恢复 |
| P-8 | 管理员可**查看全部预约条目**并代学生创建、取消预约（需记录操作原因，留痕） |
| P-9 | 管理员可**现场手动登记违约**（针对任意在座/预约用户），登记时须填写违约类型与说明 |
| P-10 | 管理员可处理**全部投诉**并填写反馈信息，可管理（加入/移出）黑名单 |
| P-11 | 管理员可查看**全校区全部自习室**的统计数据（柱状图、折线图），页面每 10 秒自动刷新 |
| P-12 | 运维可查看系统运行状态（CPU、内存、连接数、接口响应）与业务量级统计，**只读、不涉及个人明细数据** |
| P-13 | 黑名单用户在限制期内**禁止预约**，但仍可查询本人记录、提交投诉与申诉 |

## 3. 禁止规则（Prohibition Rules）

| 编号 | 规则内容 |
|------|----------|
| F-1 | **预约的开始时间不得是过去的时间点**；结束时间必须晚于开始时间 |
| F-2 | 同一学生在**同一时段内不得预约两个时间上重叠的座位**（两个预约的时段不得冲突） |
| F-3 | 学生（非管理员）**禁止查询、修改、删除他人的任何数据**（预约、违规、投诉、个人信息等） |
| F-4 | 状态为"维护中"或"停用"的座位**禁止被预约** |
| F-5 | 已开始且已过签到窗口（开始后 15 分钟）的预约**禁止取消**，只能按违约流程处理 |
| F-6 | **禁止代他人签到或签退**；签到签退操作人与预约人必须一致 |
| F-7 | 学生**禁止手动登记他人违约**、禁止修改本人违约记录；违约记录仅可申诉，由管理员处理 |
| F-8 | 黑名单用户在限制期内**禁止发起新预约**（P-13 除外） |
| F-9 | 运维**禁止查看学生个人明细数据**（姓名、学号、违约明细、投诉内容），只能看到脱敏后的量级统计 |
| F-10 | 管理员**禁止删除违约记录与操作日志**（只可标记为"申诉成立/撤销"并留痕），保证信用治理可审计 |
| F-11 | 对同一预约**禁止重复评价**；投诉反馈一经提交不得由学生修改 |

## 4. 计算规则（Computation Rules）

| 编号 | 规则名称 | 计算方式 |
|------|----------|----------|
| C-1 | **超时未签到违约** | 当前时间 > 预约开始时间 + 15 分钟 且 未签到 ⇒ 自动记录违约（类型：超时未签到），预约自动取消并释放座位 |
| C-2 | **未签退违约** | 当前时间 > 预约结束时间 + 15 分钟 且 已签到未签退 ⇒ 自动记录违约（类型：超时未签退） |
| C-3 | **早退违约** | 签到后签退时间早于预约结束时间 30 分钟以上 ⇒ 记录违约（类型：提前离开），早退部分座位时长回收 |
| C-4 | **手动违约** | 管理员现场登记的违约（如占座、违规使用），权重与自动违约相同 |
| C-5 | **违约计分** | 每条违约记录计 1 分，按自然学期滚动统计（学期初清零） |
| C-6 | **黑名单判定** | 学期内累计违约分 ≥ 3 分 ⇒ 自动加入黑名单，限制期 = 7 天 ×（进入黑名单次数），上限 30 天；限制期满自动移出 |
| C-7 | **座位状态实时计算** | 座位状态 = 停用/维护中（管理员设置优先）> 使用中（当前时刻落在某已签到预约区间内）> 已预约（当前时刻落在未开始预约区间内，且距开始 < 15 分钟）> 可用 |
| C-8 | **座位利用率** | 利用率 = 时段内已使用座位时长 /（可用座位数 × 时段总时长）× 100% |
| C-9 | **预约履约率** | 履约率 = 正常签到且正常签退的预约数 / 总预约数 × 100% |
| C-10 | **违约率** | 违约率 = 产生违约的预约数 / 总预约数 × 100% |
| C-11 | **统计刷新** | 数据分析页面（柱状图、折线图、统计数据）每 10 秒自动刷新一次 |

## 5. 角色与对象范围限制（Role & Object Scope）

### 5.1 学生（STU）范围限制

- **可操作**：预约、取消预约、签到、签退、评价、投诉、申诉。
- **对象范围**：**仅限本人创建的数据**——只能预约给自己（不能替他人预约），只能取消/签到/签退**本人的预约**，只能查看**本人的**预约记录、违规记录、投诉及反馈、评价。
- **数据可见范围**：座位实时状态为**全局可见**（只读，用于选座）；但座位的**历史使用记录、他人预约人身份**不可见（仅显示"已占用"）。

### 5.2 管理员（ADM）范围限制

- **可操作**：资源维护、预约条目管理、手动违约登记、投诉处理与反馈、黑名单管理、用户信息管理、统计分析查看。
- **对象范围**：**所管辖的全部自习室**（本系统为单一校区，即全部自习室）内所有座位、所有预约条目、所有使用记录、所有用户（仅业务字段，不含密码等凭证）；违约登记与投诉处理范围为**管辖自习室内发生的全部记录**，不限是否本人创建。
- **不可操作**：删除违约记录与审计日志（F-10）、修改系统级配置（属运维职责）。

### 5.3 运维（OPS）范围限制

- **可操作**：查看系统运行指标（CPU/内存/连接数/接口响应时间）、业务量级监控（当前预约数、签到数、在线用户数）、系统日志（技术层面）。
- **对象范围**：**全部系统的技术与性能数据**；**不包含**学生个人明细、违约明细、投诉内容等业务敏感数据（F-9）。
- **不可操作**：任何业务数据的增删改（座位、预约、违约、投诉、黑名单一律只读甚至不可见）。
