## 0. 这份文件怎么用（预计 15 分钟/条，11 条约 3 小时）

1. **只读本文件**。每条都给了：原文摘录（带章节号）、冲突到底卡在哪、2～3 个选项及各自代价、以及"选了这个要顺手改哪里"。
2. **先看"一句话"**。如果一眼能选，直接跳到"▼ 在此填写"，不用读完整段。
3. **决定必须写成可检验的表述**，不能写"按推荐""看情况""合理即可"。判断标准见下表。
4. **填完交给基线维护人**（见 §2），由其对《接口与关键设计说明书》统一同步。该说明书的同步权集中在一人手里，避免多人同时改造成冲突。
5. **一条决定四项齐全才算关闭**：人已作出决定 ＋ 受影响条目已在文档同步 ＋ 预期结果可检验 ＋ 另一成员已复核。只填了模板未同步文档的，只能标"已决定待同步"。

### 0.1 什么样的回答算合格

| 场景 | ❌ 不合格 | ✅ 合格 |

| 枚举取值 | "现场违规类型就那几个" | "`kind` 仅允许 `ON_SITE`；细分类型放在 `reason` 文本，不进枚举" |

> 自检口诀：**你的决定能不能直接翻译成一行比较运算符、一个枚举集合、或一个公式？** 能，就算合格。

### Q-03　取消与早退的 30 分钟边界：恰好整 30 分钟算不算？

| 项 | 内容 |
| --- | --- |
| 阻塞 | **是** —— API-07（取消）、API-09（早退违约） |
| 责任方 | 业务确认人 |
| 一句话 | 需求只写了"提前 30 分钟"，没写 30 分 00 秒那一刻是"还来得及"还是"已经晚了"；同一个问题出现两次（取消、早退），必须一次定完 |

**上下文（原文摘录）**

- BR-05 只写"提前 ≥30 分钟取消"，未写开闭；AV-10 又写"按 BR-05 定稿口径执行"，形成循环引用，等于没人给出比较符。（§2.4 Q-03）
- 接口现状：API-07 前置写 `now <= startsAt - 30min`（**含等于**），并注明"具体比较符待 Q-03"。（§4.7 前置与后置）
- 早退侧：API-09 后置写"若 `now <= endsAt - 30min` 则**必须**记 1 条 `EARLY_LEAVE`"，测试 TC-API09-03 写"早退 29 分钟不记违约（边界依 Q-03 同类口径）"。（§4.9、§4.9 测试关联）
- 即：**一次决定同时定两处比较符**，且正确的做法是两处都朝"对用户有利"方向取，这需要你明确同意。

**三个选项**

| 选项 | 含义（可检验表述） | 代价 / 影响 |
| --- | --- | --- |
| A. 两处都含等于 | 取消：`now <= startsAt - 30min` 可取消；早退：`now <= endsAt - 30min` 记违约 | 数学上一致（都写 `<=`），但对用户倾向相反：取消变宽松、早退变严格。容易出现"提前 30 分整不能取消但被算早退"的吐槽 |
| B. 两处都不含等于 | 取消：`now < startsAt - 30min`；早退：`now < endsAt - 30min` 才记违约 | 同样一致（都写 `<`），倾向也相反：取消变严格、早退变宽松。实践中"差 1 秒就取消不了"投诉最多 |
| **C. 一律对用户有利（推荐）** | 取消：`now <= startsAt - 30min`（含）；早退：`now < endsAt - 30min` 才记违约（不含） | 两处比较符方向不同，但语义统一为"边界值不算刁难用户"。实现上是两个不同常量，需在文档写清，避免实现者"顺手对称"改错 |

**选了这个要顺手改哪里**

- A：§4.7 前置、§4.9 后置、§5.1.1 ST-02/ST-04 守卫 —— 全部已写 `<=`，**无需改**，只需把"待 Q-03"改成"已定：含等于"。
- B：上述四处 `<=` 改 `<`，并新增 TC-API07-03 期望值（恰好 30 分钟 → `CANCEL_TOO_LATE`）。
- C：API-07/ST-02 保持 `<=`；API-09 的早退判定与 ST-04 改为 `<`；TC-API09-03 的"29 分钟"改为"恰好 30 分钟不记违约、29:59 记违约"。

**▼ 在此填写**

| 填写项 | 你的决定 |
| --- | --- |
| 选项（A / B / C） | **C. 一律对用户有利** |
| 取消边界的比较式（写到运算符） | `now <= startsAt - cancelLeadMinutes` 可取消（**含等于**，即距开始恰好 30 分钟仍可取消） |
| 早退判定的比较式（写到运算符） | `now < endsAt - earlyLeaveThresholdMinutes` 记 `EARLY_LEAVE`（**不含等于**，即距结束恰好 30 分钟签退不记违约） |
| 依据（需求条款 / 制度 / 教学设定） | BR-05 只规定"提前 ≥30 分钟"，未定开闭，属实施细则；AV-10 自身循环引用无口径。教学设定：边界值取对用户有利方向，避免"差 1 秒被罚"的申诉成本 |
| 决定人 姓名·角色·日期 | 苏帅栋 · 业务确认人（教学模拟确认）· 2026-11-26 |
| 复核人 姓名·日期 | 待复核 |
| 状态 | 已决定待同步 |

### Q-04　签到窗口下界：开始那一刻（14:00:00）能不能签到？

| 项 | 内容 |
| --- | --- |
| 阻塞 | **是** —— API-08 |
| 责任方 | 业务确认人 |
| 一句话 | 需求写"开始**后** 15 分钟内"，字面排除"开始当刻"；若按字面，14:00:00.000 点签到会被拒 1 秒之差，学生会认为系统坏了 |

**上下文（原文摘录）**

- P-5 / BR-08："预约开始后 15 分钟内签到"。（§2.4 Q-04）
- 接口现状：`startsAt <= now <= startsAt + 15min`（**含开始当刻**），标 ❓Q-04。（§4.8 前置与后置）
- 关联验收：AV-11（签到窗口边界复验）、TC-API08-02（窗口前 1 分钟被拒）、TC-API08-03（窗口后 1 分钟被拒）。（§4.8）
- 注意：窗口上界目前是**含** `+15min`（14:15:00 仍可签）。若你只改下界而不表态上界，实现者会问"为什么上界含、下界不含"，建议一并写明。

**三个选项**

| 选项 | 含义（可检验表述） | 代价 / 影响 |
| --- | --- | --- |
| **A. 含开始当刻（推荐）** | 允许条件 `startsAt <= now <= startsAt + 15min` | 只改一句"取决于 Q-04"为"含等于"。避免时钟抖动误伤；与 Q-03 选项 C 的"边界不刁难用户"一致 |
| B. 严格"开始后" | 允许条件 `startsAt < now <= startsAt + 15min` | 需改 BR-08 措辞或加注，且测试要构造"14:00:00.000 被拒"这种极难稳定复现的用例 |
| C. 允许提前 N 分钟签 | 允许条件 `startsAt - N <= now <= startsAt + 15min`，N 进规则参数表 | 体验最好，但等于改 BR-08 规则本身，还需在 API-19 参数表新增 `checkInWindowBeforeMinutes`，链条变长；S1 不建议 |

**选了这个要顺手改哪里**：§4.8 前置与后置、§5.1.1 ST-03 守卫、（C）§4.19 `params` 列表 + §5.2 校验链第 4 步。

### Q-06　FR-07 的"按区域筛选"：数据模型里没有"区域"这个字段

| 项 | 内容 |
| --- | --- |
| 阻塞 | **是** —— API-04（查询参数） |
| 责任方 | 预约模块负责人 |
| 一句话 | 需求要按"区域"筛座位，但座位表里只有编号 + 标签，没有区域；要么用标签冒充，要么加字段，要么把"区域"从需求里删掉 |

**上下文（原文摘录）**

- FR-07 要求按"日期/时段/自习室/区域/标签"筛选座位。（§2.1 FR-07 行）
- 数据字典 DD02 的座位属性只有 `seatLabel` 与 `features`（标签数组），**无区域字段**。（§2.4 Q-06）
- 接口现状：API-04 只有 `feature` 参数（按标签模糊匹配），没有 `zone`/`area` 参数，且注明"`feature` 语义由前端标签约定 ❓Q-06"。（§4.4 请求行）
- 由此产生的实际风险：若选"用标签冒充"，管理员录入时写"靠窗"还是"窗边"完全自由，同义标签会让筛选结果不稳定。

**三个选项**

| 选项 | 含义 | 代价 / 影响 |
| --- | --- | --- |
| A. 用标签模拟区域 | 约定区域也是 `features` 的一个值（如 `靠窗区`），API-04 不新增参数 | 零改动；但筛选正确性依赖录入规范，且无法做"区域内座位编号唯一"这类校验 |
| B. 新增 `seat.zone` 字段 | API-04 新增 `zone` 参数；API-13c/13d 请求体新增 `zone`；API-04 响应新增 `zone`；DD02 与 §5.3 表结构同步 | 语义最清晰、可校验、可做区域级统计；代价是"建表时就要有"，S1 数据库表需加一列，且 4 处文档要改 |
| C. 从需求中删除"区域"维度 | FR-07 改为"按日期/时段/自习室/标签筛选" | 零成本，但属需求变更，需需求文档维护人签字，并留痕说明"因数据模型无对应字段" |

**为什么必须先定**：这决定 S1 的 `seat` 表结构。若先按 A 实现、S2 再改 B，需数据迁移 + 前端改造；反之若先建了 `zone` 但最终用 A，只是多一列空值，代价小。**若拿不准，倾向 B**（成本前置、不可逆性最低）。

**▼ 在此填写**

| 填写项 | 你的决定 |
| --- | --- |
| 选项（A / B / C） | **B. 新增 `seat.zone` 字段** |
| 若 A：区域标签的命名规范（列 3～5 个允许值） | 不适用（未选 A） |
| 若 B：`zone` 是否必填、允许值来源（字典表 / 自由文本） | **必填**（建表时给存量座位回填一个默认值，如 `A区`）；允许值来源为**字典表**（`zone_dictionary`，管理员可维护，禁止自由文本），因此"区域内座位编号唯一性""区域级统计"才能成立 |
| 若 C：FR-07 的新措辞 | 不适用（未选 C） |
| 决定人 姓名·角色·日期 | 苏帅栋 · 预约模块负责人（教学模拟确认）· 2026-11-26 |
| 复核人 姓名·日期 | 待复核 · 待填（不得为本决定人） |
| 状态 | 已决定待同步 |

> **选择理由（要点）**：A 会让筛选正确性依赖录入规范（"靠窗"还是"窗边"），且区域一旦要用作统计维度就无法补救；C 属需求变更、要删已批准的功能维度。B 的成本前置但不可逆性最低——先建列后弃用只是空列，反之先按 A 实现再改 B 需要数据迁移与前端改造。

**验收样例**：房间内 5 座（A 区 3、B 区 2）。查询 A 区 → 只返回 3 条，且 `meta.total=3`；不带区域参数 → 返回 5 条。

### Q-07　"维护中"和"停用"是同一种状态吗？

| 项 | 内容 |
| --- | --- |

### Q-24　账户被停用时，该用户已有的未来预约怎么处理？

| 项 | 内容 |
| --- | --- |
| 阻塞 | 否（但不定会留下一个必然后果，见下） |
| 责任方 | 业务确认人 |
| 一句话 | 账号一停，人登不上来，可他名下的预约还在；到了时间点，自动扫描会判他"未签到"违约并扣分——封号还被记违约，合理吗 |

**上下文（原文摘录）**

- ADR-1 只写"停用后所有接口不可用"，**未要求**取消预约；接口现状："未来预约**不自动取消** ❓Q-24"。（§4.18.2 后置）
- 自动违约任务 T-1 的条件只看预约状态与时间：`status='BOOKED' AND starts_at + checkInWindow < now` → 不看用户账号状态。（§5.6）
- 因此当前契约的**必然结果**：停用用户在未来 1 天内会被记 N 条 `NO_SHOW`，学期分 +N，可能直接触发黑名单（阈值 3 分）。（§5.5、§5.6 联合推导）
- 这是本条最需要业务方拍板的事实：**停用是管理处罚，违约处罚是否要叠加？**

**三个选项**

| 选项 | 含义 | 代价 / 影响 |
| --- | --- | --- |
| A. 不取消（现状） | 预约保留，到期由 T-1 判 `NO_SHOW` | 零改动；但"停用 → 自动累加违约分 → 进黑名单"叠加处罚，学生复号后可能发现已被封 7 天，申诉成本高 |
| **B. 停用时取消其全部未来 `BOOKED`（推荐）** | 状态改 `CANCELLED`，**不记违约**，逐条写审计；返回值新增 `cancelledReservations` 计数 | 语义清晰："人不能来，座位释放给别人"；需改 §4.18.2 后置与响应体、§5.7 API-18b 事务行（+ 删除占用记录），并加 1 组测试 |
| C. 停用期间冻结扫描判定 | T-1/T-2 查询条件增加"用户 `accountStatus=ACTIVE`" | 预约不取消但也不判违约；代价：座位被"僵尸预约"占着直到结束，且查询需 join 用户表（破坏 I-3 索引的单纯性），实现最复杂 |

**若选 B 需同步**：§4.18.2 后置不变量与成功响应；§5.7 API-18b 行改为"用户状态 + 取消的预约(N) + 删除占用(N) + 审计(N)"；§5.4 锁顺序（API-18b 现为 `L4 → L1`，取消预约需再加 L3）；Q-12（工作三）的终止口径不受影响（那是座位停用，不是账号停用）。

**▼ 在此填写**

| 填写项 | 你的决定 |
| --- | --- |
| 选项（A / B / C） | **B. 停用时取消其全部未来 `BOOKED` 预约，不记违约** |
| 若 B：取消是否写审计（建议写）、是否给用户通知（S2） | **写审计**（逐条记录被取消的 `reservationId`、操作人、原因）；**通知**归入 S2 站内通知中心（S1 阶段仅落审计，不做投递） |
| 若 C：冻结期间预约是否仍显示"已预约"给其他学生 | 不适用（未选 C）|
| 决定人 姓名·角色·日期 |  |
| 复核人 姓名·日期 | 待复核 |
| 状态 | 已决定待同步 |

> **为什么必须定（A 的后果）**：T-1 只按"预约状态 + 时间"扫描（§5.6），不看用户账号状态。若保留现状 A，被停用的学生在 1 天内会被记 N 条 `NO_SHOW`，学期分直达 3 分阈值 → 自动进黑名单 7 天。**停用（管理处罚）与违约（履约处罚）叠加**，学生恢复账号后还要申诉，这是本系统最容易被投诉的设计。
>
> **落地口径（供实现直接照抄）**：
> - 后置不变量：该用户所有 `status='BOOKED' AND startsAt > now` 的预约改为 `CANCELLED`；对应占用记录删除；违约表**零新增**。
> - 成功响应新增 `cancelledReservations`（int）。
> - 事务范围扩为：用户状态 + 取消的预约(N) + 删除占用(N) + 审计(N)。
> - 锁顺序从 `L4 → L1` 改为 `L4 → L1 → L3*`（按 `reservation_id` 升序批量加锁，避免与预约接口交叉死锁）。

### Q-25　改业务规则参数（如签到窗口 15→20 分钟）要不要更高权限？

- API-19：GET 与 PUT 均为 ADM；"PUT ❓是否要求更高权限（学校管理部门）见 Q-25"。（§4.19 调用者及权限）

| 选项 | 含义 | 代价 / 影响 |

| **A. ADM 可改 + 强制 reason + 审计（推荐）** | 维持现状，但 `reason` 内容规范要求写明审批依据与批准人 | 零改动；与 HD-07 的差异靠"制度 + 留痕"弥补，验收时以审计记录证明合规 |
| B. 新增角色/权限位 | 如 `SUPER_ADM` 或 `ADM` 加 `canEditParams` 权限位 | 最贴合 HD-07；代价：§3.2 令牌 `role` 枚举、§3.3 判定表、权限矩阵、登录/前端菜单全部同步，S1 工作量显著增加 |
