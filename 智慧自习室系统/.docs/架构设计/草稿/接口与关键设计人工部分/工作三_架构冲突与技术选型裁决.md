### Q-18　测试能不能直接改数据库里的时间字段来构造场景？

| 项 | 内容 |
| --- | --- |
| 阻塞 | **是** —— §3.8、§5.6 |
| 责任方 | 测试责任人 + 后端（联署） |
| 一句话 | 要验"停机 3 天后开机能否补齐违约"，不可能真等 3 天；不能改服务器时间，那改数据库里的 `starts_at` 行不行 |

**上下文（原文摘录）**

- §3.8：业务"现在"只有两个来源——① 接口内调用时的服务端时钟；② 扫描任务的批处理时刻 `scanRunAt`。"所有时间比较以服务器时间为准，不信任客户端时间。"（§3.8）
- ❓Q-18 原文："测试要求'通过调整数据库中预约单的时间字段构造场景'，则业务时钟读取的是**字段值**而非系统时间。这条对隔离级别与缓存有影响（§5.6），需确认构造场景的合法范围（**不得改服务器时间**）。"（§3.8）
- 现有测试已依赖此类构造：AV-03（漏跑补偿）、TC-API12-04（学期跨境清零）、TC-API16-09（与扫描并发）、工作二的 Q-09 数值样例。（§5.6、§4.12）
- 实际机制：T-1 的条件是 `status='BOOKED' AND starts_at + checkInWindow < now`。把 `starts_at` 改成 3 天前，条件自然成立——**只要"now"始终是真实服务器时间，就无需改时钟**。

**三个选项**

| 选项 | 含义 | 代价 / 影响 |
| --- | --- | --- |
| **A. 允许改表内时间字段（推荐）** | 测试可改 `reservation.starts_at/ends_at/checked_in_at`、`violation.created_at`、`blacklist_until`、`rule_parameter.semester_start`；**禁止**改服务器时间、禁止改业务代码里的"now" | 零设计改动；但必须把"判定表达式只用字段值与 `now()`"写成红线，否则某个实现者若缓存了"预约快照时刻"就会失效。需在 §5.6 增一句"任何判定不得依赖缓存中的相对时间" |
| B. 注入可配置业务时钟 | 代码里所有"now"从一个 `Clock` 抽象取，测试可注入偏移（生产固定系统时钟） | 最干净、可测性最好；代价是 S1 增加一层抽象 + 一个开关，且"忘了走 Clock"的地方会产生难查的不一致；还需防止生产误开 |
| C. 只等真实时间 | 不改任何东西，靠真实时间流逝 | AV-03、TC-API12-04 无法在课程周期内验收 → **不可行** |

**选 A 必须一并确定的边界**（这些字段被"改造"后，语义会短暂不真实，需要测试环境隔离）：

### Q-02　1 小时整点网格，碰上"开始后 15 分钟内还能取消"，占用记录怎么办？

| 项 | 内容 |
| --- | --- |
| 阻塞 | **是** —— API-06/07/08/09、T-1/T-2 |
| 责任方 | 预约模块负责人 + 架构负责人（联署） |
| 一句话 | 14:00–15:00 的预约在 14:05 被取消，那一小时到底释放给别人、还是继续占着？网格模型只有整格，没有"剩下的 55 分钟" |

**上下文（原文摘录）**

- ADR-002：1 小时固定网格，"跨小时拆分为多条连续记录"，占用是**离散记录** `(seat_id, slot_start)`，不支持碎片时段。（§2.4 Q-02、§5.2）
- 决策表 7.2 / BR-05 / F-5：预约开始后 15 分钟内**仍可取消**（即取消可能发生在时段开始之后）。（§2.4 Q-02）
- 决策表 7.3 / C-2：超时未签退可在 `endsAt + grace` 之后**再判违约**（状态在时段内可能变化）。（§2.4 Q-02）
- **冲突的真实形态**（这一步必须看懂）：若 14:05 取消后**保留** 14:00–15:00 的占用记录，则按 C-7（§5.1.3）该座位会显示为 `AVAILABLE`（因为没有 `BOOKED`/`CHECKED_IN` 预约），但别人提交 API-06 时会被 U-1 唯一约束挡住 → **"显示可约却约不上"**，正好违反 §4.5 "API-05 与 API-06 必须共用同一领域函数"。（§5.1.3、§4.5、§5.3 U-1）
- 因此"保留占用"不是可行选项；真正的选择只有下面三种。

**三个选项**

| 选项 | 含义（可检验） | 代价 / 影响 |
| --- | --- | --- |
| A. 禁止开始后取消 | 取消窗口只到 `startsAt - 30min`（即 F-5 的"开始后 15 分钟内可取消"作废）；状态变更只可能在网格边界前后 | 契约最简单（与 Q-03 一致）；但**改需求**（决策表 7.2 R2、F-5、AV-10 需重写），且学生在路上发现来不了就只能被记违约 |

### Q-28　数据库选哪家？U-1/U-8 的"部分唯一索引"怎么落？

| 项 | 内容 |
| --- | --- |
| 阻塞 | **是** —— §5.3 U-1/U-8 |
| 责任方 | 架构负责人 |
| 一句话 | 原型 SQLite、基线 MySQL，而 U-1/U-8 要求"只对有效记录生效"的唯一约束——MySQL 不支持部分索引，必须换写法；不定就没法建表 |

**上下文（原文摘录）**

- 原型用 SQLite；基线 §3.1 写 MySQL。❓Q-28。（§5.3 末）
- U-1：`UNIQUE(seat_id, slot_start)` on `seat_occupancy`，"且只对**有效占用**生效 ❓"。（§5.3）
- U-8：同一用户至多 1 条 `until > now` 的黑名单记录（"部分索引 ❓"）。（§5.3）
- §5.4 锁落地：L2 用 `SELECT ... FOR UPDATE` 锁 `seat` 行；"SQLite 无行锁，等价于写事务串行化（`BEGIN IMMEDIATE`）"。（§5.4 注）
- §5.3 已给提示："SQLite 与 PostgreSQL 支持 `CREATE UNIQUE INDEX ... WHERE`；MySQL 不支持部分索引，只能用生成列 + 唯一约束。"（§5.3）
- 若 Q-02 选碎片模型（C），还需要区间排他约束 → 实际只有 PostgreSQL 原生支持。

**三个选项**

| 选项 | U-1 实现 | U-8 实现 | 锁落地 | 代价 / 影响 |
| --- | --- | --- | --- | --- |
| **A. PostgreSQL（推荐）** | 部分唯一索引 `CREATE UNIQUE INDEX u1 ON seat_occupancy(seat_id, slot_start) WHERE released_at IS NULL` | 同法部分索引 | `SELECT ... FOR UPDATE` 原生 | 能力最全（部分索引、行锁、排他约束、`SKIP LOCKED` 便于扫描任务分片）；代价：需在服务器装 PG，运维要会；若课程环境只给 MySQL/SQLite 则不适用 |
| B. MySQL 8 | 生成列 `active_slot_start AS (IF(released_at IS NULL, slot_start, NULL))` + `UNIQUE(seat_id, active_slot_start)` | 生成列 `active_until AS (IF(released_at IS NULL, blacklist_until, NULL))` + `UNIQUE(user_id)` | 行锁可用 | 基线一致；代价：生成列方案须"在本文档登记后才可写代码"（原文要求），且 NULL 唯一性语义（MySQL 允许多个 NULL）正好符合"失效记录不参与唯一"的意图 |
| C. SQLite | 原生部分索引（支持） | 同法 | **无行锁**：`BEGIN IMMEDIATE` 全局写锁 | 零部署，课程演示最省；代价：并发测试语义与生产不同（全部写串行），Q-02 的"并发抢占"测试实际测不到真实竞争；且 `FOR UPDATE` 语法不支持，§5.4 整套锁顺序需改写为"全局写锁"口径 |

**注意**：若 Q-02 选了"C 区间占用模型"，A 是唯一能低成本支持排他约束的选择（PG `EXCLUDE`）；B 需要触发器或应用层校验；C 只能应用层校验。**Q-02 与 Q-28 应同一次会议定**。

### Q-29　锁等 5 秒还没拿到，返回 409 还是 425？

| 项 | 内容 |
| --- | --- |
| 阻塞 | 否 |
| 责任方 | 架构负责人 |
| 一句话 | 两个人抢同一格时，后到者等锁超时了；告诉他"被占了，换一个"还是"稍后重试" |

**上下文（原文摘录）**

- §5.4 注："锁等待超时默认 5 秒，超时返回 `409 SLOT_TAKEN`（视同抢占失败，而不是 500），并记审计。❓Q-29：是否应返回 `425 Too Early` 让前端自动重试 1 次，还是直接 `409` 让用户重选？本文档取 409（简单、语义明确）。"（§5.4）
- 现有错误码表里 `SLOT_TAKEN` 的语义是"目标座位目标时段已被有效预约占用（含并发抢占失败）"——已涵盖锁超时情形。（§3.4）
- 若新增 425 → 需在 §3.4 登记新码，并在 §3.1 状态码范围里加 425，前端需实现"自动重试一次"的逻辑（且需幂等键配合，碰巧已有）。

**三个选项**

| 选项 | 含义 | 代价 / 影响 |
| --- | --- | --- |
| **A. 409 `SLOT_TAKEN`（推荐，现状）** | 前端提示"该时段已被占用，请重新选择" | 零改动，语义明确；缺点：锁超时其实可能"没人占"，只是争抢激烈，提示语略失真（可在 `fields.reason=LOCK_TIMEOUT` 里区分，前端不展示） |
| B. 425 Too Early + `Retry-After: 1` | 前端自动重试 1 次，仍失败再提示 | 体验更好；代价：新错误码、新状态码范围、前端重试逻辑、测试用例；且 425 在浏览器/代理中的处理不一致，课程环境下收益有限 |
| C. 409 + `fields.reason` 细分 | 状态码不变，负载里区分 `OCCUPIED` / `LOCK_TIMEOUT` | 折中；前端可据此决定"换座位"还是"再点一次"；代价：仅在契约里加一个字段（成本极低） |
