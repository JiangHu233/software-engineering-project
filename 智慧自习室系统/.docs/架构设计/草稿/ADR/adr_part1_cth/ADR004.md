# ADR-004 / 投诉处理时限从提交起算并以统计体现超时

## 状态

已接受

## 背景

关联需求"投诉需在候选 3 个工作日内处理完毕"及 KQ-04。

当前系统存在两个待定口径：

1. 时限起算点为用户**提交时刻**还是后台**受理时刻**；
2. 超时后是否触发**自动催办**流程，还是仅在**统计报表**中体现。

起算点与超时处理方式直接影响投诉模块状态机的状态迁移规则及超时统计口径，需在开发前统一。

## 比较

| 备选方案 | 说明 | 收益 | 代价 |
|---------|------|------|------|
| 备选一：从受理起算 + 超时催办 | 时限从后台受理时刻起算，超时自动催办 | 后台处理时间充足，超时有主动干预 | 用户提交后若长时间未受理，等待时间不计入时限，用户权益受损；催办需额外实现通知与升级机制，当前阶段复杂度过高 |
| 备选二：从提交起算 + 超时催办 | 时限从用户提交时刻起算，超时自动催办 | 对用户最有保障且超时有干预 | 催办流程依赖消息通知与人员调度，超出本期实现范围 |
| 备选三：从提交起算 + 统计体现超时 | 时限从用户提交时刻起算，超时仅在统计报表中体现 | 起算口径对用户公平，统计实现成本低，可通过报表暴露超时情况供管理端跟进 | 超时投诉无主动提醒，存在滞留风险 |

## 决定

采用**备选三**：投诉处理时限从**用户提交时刻**起算，超时不触发自动催办，仅在统计报表中体现。

明确不采用：

- 从受理时刻起算的口径；
- 本期不实现超时自动催办流程。

## 理由

1. **从提交起算口径清晰、对用户透明**，避免因受理延迟变相延长处理时限，符合投诉处理保护用户权益的业务定位。
2. **仅统计体现超时的方案与当前团队规模、开发周期匹配**，先以数据暴露问题，为后续引入催办机制提供依据。

## 代价

- 受理延迟将计入处理时限，可能推高统计口径下的超时率，需同时关注受理效率；
- 超时投诉不会自动提醒处理人，存在滞留风险；
- 需明确"工作日"的节假日规则，否则统计口径有歧义。

## 验证

1. 为投诉模块状态机编写单元测试，覆盖"提交 → 受理 → 办结"各状态的时间戳记录；
2. 构造跨周末与节假日的测试数据，验证 3 个工作日的计算与超时判定；
3. 验证统计报表能按起算口径正确标识超时投诉。

结果存于 `docs/evidence/adr-004`。

## 重新评估条件

- 投诉量显著增长且超时率超过管理阈值；
- 上级或监管要求超时必须主动催办；
- 节假日规则发生变化。
