1. **业务规则取值**：一律引用《需求规格说明书》与已接受的 ADR，本文档不新造规则，只把规则翻译成可检验的接口契约。凡发现规则之间存在张力（例如 BR-06 碎片时段与 ADR-002 固定网格冲突），v1.0 曾登记为开放项（§2.4）并标 ❓；**v1.1 起这些张力已全部裁决（§2.4 保留记录 + §7.2 台账）**，后续若发现新矛盾，按同一流程登记，不自行补全。
2. **阶段划分**：本文档假设 S1 范围见 §1.2。该假设与《分阶段实现与测试计划》的正式阶段表冲突时，以阶段计划为准，接口编号不变、只调整归属阶段。
3. **实现技术细节**：基线版架构层对技术栈的表述存在内部不一致（§5.9 有登记）。本文档用**语言无关**的方式描述锁、事务与隔离级别；落到具体框架时须回填框架级实现，不得改变本文档定义的语义。

## 3. 全局接口约定

> 本章的约定对 §4 全部接口生效。任何接口的契约条目与本约定冲突时，以本约定为准并在 §4 标注偏离。

### 3.1 版本、风格与统一响应包

- 风格：REST 风格，路径使用**复数名词 + 子资源**（`/reservations/{id}/check-in`）。动作型操作以子资源 POST 表达，不使用 `/doCheckIn` 之类动词路径。
- 版本：路径前缀 `/api/v1`。字段的**新增**不算破坏性变更；字段的删除、改名、语义变化、错误码语义变化必须升 `/api/v2` 或在 §4 登记为破坏性变更并经三方确认。
- 命名：请求与响应一律 `camelCase`；时间一律 ISO-8601 本地时间（`2026-12-01T09:00:00`，无时区后缀，服务器与数据库统一使用同一时区，依据 AS-03）；日期一律 `YYYY-MM-DD`。
- **24:00 的表示（统一约定）**：ISO-8601 不允许 `T24:00:00`。因此 `closeHour=24` 时的"当天结束"一律写成**次日 `T00:00:00`**（例：`2026-12-01` 22:00–24:00 → `endsAt="2026-12-02T00:00:00"`）；`from`/`to` 的 `HH:mm` 同理**不得**写 `24:00`，需要表示"到当天结束"时用 `to=23:59` 或省略 `to`（省略即整天）。
- 成功响应统一结构：

```json
{ "data": { }, "meta": { } }
```

- 失败响应统一结构：

```json
{ "error": { "code": "STRING_CODE", "message": "面向用户的中文提示", "fields": { }, "rule": "BR-05", "requestId": "…" } }
```

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `error.code` | string | 是 | 机器可判别的错误码，取自 §3.3 表；**前端只依据 code 分支**，不解析 message |
| `error.message` | string | 是 | 面向用户的提示文案，不得包含内部字段名、SQL、堆栈 |
| `error.fields` | object | 否 | 字段级校验错误，键为请求字段名，值为错误说明数组 |
| `error.rule` | string | 否 | 命中的规则编号（BR/P/F/C）或 `KQ` 编号，满足 §8.1"返回规则编号或原因" |
| `error.requestId` | string | 是 | 服务端生成的请求标识，写入审计日志，便于用户报障时定位 |

- 状态码使用范围：`200` 成功、`201` 资源创建成功并返回 `Location`、`400` 请求格式非法、`401` 未认证、`403` 已认证但越权、`404` 资源不存在、`409` 状态冲突/并发冲突、`422` 语义校验失败（业务规则拒绝）、`429` 触发频控、`500` 未预期错误。

> 区分 `400` 与 `422`：**格式**错误（缺字段、类型错、越界、非整点）用 `400` + `VALIDATION_FAILED`；**业务规则**拒绝（黑名单、时段被占、状态不对）用 `422`/`409` + 业务码。前端据此决定是"表单提示"还是"业务提示"。

### 3.2 认证与会话载体

> v1.1 已按 **Q-17 裁决 A** 固定：Bearer + 8 小时 + 无刷新 + 多会话。

| 项 | 约定 |
| --- | --- |
| 认证方案 | 自建账号体系，凭据为用户级 JWT（ADR-12）。**固定使用** `Authorization: Bearer <token>`；**不采用** Cookie 承载（因此无需 CSRF token，NFR-09 的输入校验仍适用） |
| 令牌载荷 | `sub`（用户 ID）、`role`（`STU`/`ADM`/`OPS`）、`jti`（令牌唯一 ID，用于登出吊销）、`iat`、`exp`。**不得**放入学号、姓名、违约记录等个人信息（NFR-08） |
| 有效期 | `exp = iat + 8 小时`（可由参数 `tokenTtlHours` 配置，默认 8，范围 1～24）。**不引入 refresh token**，过期后接口返回 `401 UNAUTHENTICATED`，前端跳登录页 |
| 无状态校验 | 服务端每次请求都校验签名与过期，**不信任前端提交的角色**；`role` 只用于快速分支，最终权限由服务端按用户 ID 重新加载判定 |
| 会话模型 | **多会话**：同一账号可在多处登录，互不影响；每次登录签发独立 `jti` |
| 登出 | 将该令牌的 `jti` 写入吊销名单（`token_revocation`），服务端每请求校验一次；吊销记录保留到该令牌的 `exp` 之后即可清理（单表写的独立事务） |
| 会话失效 | 用户被停用（API-18）后，其已签发令牌最多在下一个请求时被拒（服务端每请求查 `accountStatus`），不依赖令牌自然过期 |
| 测试提示 | 因无刷新机制，过期行为用"改令牌 `exp`/使用过期令牌"构造，不需改服务器时间（与 §3.8 一致） |

### 3.3 认证、角色与对象范围判定（统一拦截语义）

所有受保护接口的判定顺序**必须一致**，顺序本身是契约的一部分：

| 步骤 | 判定 | 不通过时 | 是否写审计 |
| --- | --- | --- | --- |
| 1 | 令牌存在且签名有效、未过期 | `401 UNAUTHENTICATED` | 否 |
| 2 | 用户存在且 `accountStatus = ACTIVE` | `401 ACCOUNT_DISABLED` | 是（NFR-07） |
| 3 | 角色满足该接口要求 | `403 FORBIDDEN_ROLE` | 是 |
| 4 | 对象归属/数据范围满足 | `403 FORBIDDEN_OBJECT`（**不得**用 404 掩盖，因为本系统对象 ID 不含敏感信息，且需求要求"返回 403 或空列表"） | 是 |
| 5 | 业务前置状态校验 | 见各接口 | 视接口 |

对象范围（PS-01～PS-09）的落地口径：

| 角色 | 可读范围 | 可写范围 |
| --- | --- | --- |
| STU（学生） | 本人预约、本人违约记录、本人黑名单状态；全部座位实时状态（**不含占用者身份**，PS-01、NFR-08） | 仅本人名下的预约（签到/签退/取消） |
| ADM（管理员） | 全部自习室与座位、全部预约与违约记录（PS-02，口径冲突见 Q-15）、用户业务字段 | 资源维护、手动违约登记、账户状态、规则参数；**不可**代签到代签退（F-6）、**不可**删除违约记录（F-10） |
| OPS（运维） | 仅脱敏量级指标 | 无 |

黑名单用户的受限面（P-13、ADR-1）：**只拦截 API-06（创建预约）**；API-03/04/05/07/08/09/10/11/12 均不受限。账户停用（ADR-1）：登录即拒，所有接口不可用。

**数据范围与视图粒度的区分（Q-15 裁决 A）**：PS-02 的"管辖 = 全部自习室"是**权限范围**——ADM 可访问任一自习室的数据；ADR-006 的"按自习室查询、不做全校聚合"是**视图粒度**——看板类接口（API-14）一次只返回一个自习室，列表类接口（API-17）可不带 `roomId` 跨室查询。二者不冲突，实现时**不得**据此新增全校聚合接口（属 S2 变更）。

**角色相关的三条硬规则**：

| 规则 | 内容 | 依据 |
| --- | --- | --- |
| 管理员不可使系统失去全部可用管理员 | 若 PATCH API-18b 会把最后一个 `ACTIVE` 的 ADM 置为 `DISABLED`，返回 `422 LAST_ADMIN_FORBIDDEN`（`fields.activeAdminCount`） | Q-23 裁决 C |
| 规则参数修改仍属 ADM | **不新增角色**；以 `reason` 内容约束实现双人复核（审批依据 + 批准人 + 生效日期 + 变更前后值），缺失即 `400 VALIDATION_FAILED` | Q-25 裁决 C |
| 手动违约类型唯一 | `kind` 只允许 `ON_SITE`，细分情况写 `reason` | Q-22 裁决 A |

### 3.5 分页、排序、过滤与数据范围

| 项 | 约定（对所有列表接口一致） |
| --- | --- |
| 分页参数 | `page`（从 1 开始，默认 1）、`pageSize`（默认 20，最大 100，超过 100 一律返回 `VALIDATION_FAILED` 而不是静默截断） |
| 分页响应 | `meta.page`、`meta.pageSize`、`meta.total`、`meta.totalPages`；`total` 为该过滤条件下、**调用者数据范围内**的总数 |
| 默认排序 | 预约类列表：`startsAt DESC, id DESC`；违约类：`createdAt DESC, id DESC`；座位类：`seatLabel ASC`。排序键必须**唯一可定序**（末位加 `id`），防止翻页重复/遗漏 |
| 允许自定义排序 | `sort` 参数，值为白名单字段 + `,asc` 或 `,desc`；不在白名单返回 `VALIDATION_FAILED`。禁止把 `sort` 直接拼进 SQL（NFR-09） |
| 过滤 | 见各接口 query 表；未识别的 query 参数**忽略而不报错**（便于前端灰度），但白名单内的非法值必须报错 |
| 数据范围 | 服务端强制注入：STU 一律附加 `userId = currentUser`；ADM 按 PS-02；OPS 无列表接口。前端传入的 `userId` 只能作为 ADM 的过滤条件，STU 传入时忽略并覆盖为本人 |
| 时间范围 | `from`/`to` 均为本地时间，`from < to`，跨度上限 31 天（分析场景 S2 再放宽），超限 `VALIDATION_FAILED` |

### 3.7 幂等键协议（写接口通用）

**适用范围**：API-06、API-07、API-08、API-09、API-13（4 条）、API-16、API-18（PATCH）、API-19（PUT）。API-19 见 §5.8 另有版本号协议。

| 规则 | 约定 |
| --- | --- |
| 请求头 | `Idempotency-Key: <客户端生成的 UUID v4>`，**必填**。缺失时返回 `400 VALIDATION_FAILED`（`fields.Idempotency-Key`） |
| 作用域 | 幂等键的作用域为（调用者用户 ID + 接口路径 + HTTP 方法 + 幂等键），不同用户的相同键互不影响 |
| 首次请求 | 服务端登记 `(scope, key)`，状态 `IN_PROGRESS`，执行业务 |
| 成功后再来（同键同体） | 返回**首次的响应体与状态码**（重放），`meta.replayed = true`；不重复产生副作用 |
| 并发同键 | 后到者返回 `409 DUPLICATE_REQUEST`，可退避重试；已在处理的请求不受影响 |
| 同键不同体 | 返回 `422 IDEMPOTENCY_KEY_CONFLICT`，不执行业务 |
| 记录保留 | 幂等记录保留 24 小时（可配置）；过期后同键被视为新请求 |
| 不适用幂等键的情形 | 只读接口不需要该头 |

> 为什么必须强制：UC-01 验收 ④、UC-04 验收 ⑥、AV-03④、AV-06④ 都要求"重复请求只产生一条记录"。需求把幂等写成结果要求，但**未指定实现手段**；本文档把手段固定为幂等键 + 业务唯一约束双保险（§5.3），避免不同实现者各自用"查一下再插入"导致竞态。

### 3.8 时间、时区与"业务时钟"

- 服务端与数据库使用同一时区；所有时间比较以**服务器时间**为准（AS-03），不信任客户端时间。
- 业务上"现在"只有两个来源：① 接口内调用时的服务端时钟；② 扫描任务的批处理时刻 `scanRunAt`。二者都写入审计或违约记录，便于复盘。
- ✅ **Q-18（裁决 A）：允许修改数据库时间字段构造测试场景**，但**禁止**修改服务器系统时间、禁止修改业务代码中的"now"。

| 项 | 约定 |
| --- | --- |
| 允许修改的字段 | `reservation.starts_at`、`reservation.ends_at`、`reservation.checked_in_at`、`reservation.checked_out_at`、`violation.created_at`、`blacklist.blacklist_until`、`blacklist.released_at`、`rule_parameter.effective_from`、`rule_parameter.effective_to` |
| 禁止修改 | 服务器/容器系统时间；`audit_log` 任何字段（F-10）；`idempotency_record`（破坏重放语义）；`user.created_at` |
| 实现红线 | 所有判定表达式**只能**用"表字段值"与 `now()`（服务器当前时间）比较，**不得**依赖进程内缓存的"相对时间"或"快照时刻"，否则改字段后判定不生效 |
| 环境要求 | 仅在独立测试库执行；每条用例用独立数据或结束后恢复；不得在演示库执行 |
| 验收用途 | AV-03（漏跑补偿）、TC-API12-04（跨学期）、TC-API16-09（扫描并发）、Q-09 的延长公式验证 |

### 4.1 API-01 登录

| 项目 | 内容 |
| --- | --- |
| **接口编号/名称** | API-01 / 登录（签发令牌） |
| **需求与决策依据** | NFR-07（服务端强制校验）、NFR-08（口令不得明文）、ADR-12（自建账号 + 自签 JWT）、NFR-09（输入校验） |
| **方法与路径** | `POST /api/v1/auth/login` |
| **调用者及权限** | 未认证用户可调用（匿名）。账号停用者可提交但返回 `ACCOUNT_DISABLED`。黑名单用户**可以**登录（P-13、ADR-1） |
| **请求** | 请求体：`username` string 必填 1～40 字符，去除首尾空白后非空；`password` string 必填 8～72 字符（上限 72 为常见哈希算法上限，超出返回 400，**不截断**）。查询参数：无。路径参数：无。请求头：`Content-Type: application/json` |
| **成功响应** | `200`；`data.token` string（JWT）、`data.expiresAt` ISO-8601（= `iat` + 8 小时，`tokenTtlHours` 可配）、`data.user` 对象（同 API-03 的 user）、`meta.requestId`。业务状态：会话建立。**不返回 refresh token**（Q-17 裁决 A）。 |
| **失败响应** | ① 用户名/密码错误 → `401 UNAUTHENTICATED`，**不区分**"用户不存在"与"密码错误"（防枚举），数据不变；② 字段缺失/超长 → `400 VALIDATION_FAILED`；③ 账号停用 → `401 ACCOUNT_DISABLED`，数据不变并写审计；④ 频控 → `429 RATE_LIMITED`。 |
| **前置与后置** | 前置：账号存在且启用。后置：签发令牌；写入登录审计（成功/失败都记，失败只记用户名与 IP，不记口令）；成功后 `User.lastLoginAt` 更新。 |
| **并发与幂等** | 不需要幂等键（每次登录都可产生新令牌，属于预期重复）。**多会话**：同一账号并发登录不互斥，各自签发独立 `jti`，互不影响（Q-17 裁决 A）。 |
| **事务** | 单表写（审计 + `lastLoginAt`），可独立提交；令牌签发不落库。事务外副作用：无（令牌由服务端签出，不产生外部调用）。 |
| **隐私** | 响应不含口令哈希、不含违约/黑名单明细（另见 API-03）。日志禁止记录口令，禁止记录完整令牌。 |
| **测试关联** | TC-API01-01 正常；TC-API01-02 密码错；TC-API01-03 停用账号；TC-API01-04 频控；TC-API01-05 口令超长。对应 AV-16（OPS 与 ADM 边界）的前置。 |
| **确认** | 提供方：认证与账号模块负责人（待填）；调用方：前端（待填）；复核人：（待填）；版本：v1.0-draft |

**示例**

正常：
```http
POST /api/v1/auth/login
{"username":"student","password":"student123"}
→ 200
{"data":{"token":"eyJhbGciOi…","expiresAt":"2026-11-26T18:00:00",
 "user":{"userId":2,"username":"student","displayName":"演示学生","role":"STU",
         "accountStatus":"ACTIVE","blacklist":{"active":false,"until":null,"reason":null}}},
 "meta":{"requestId":"7f3c…"}}
```

业务失败：
```http
{"username":"student","password":"wrong"}
→ 401 {"error":{"code":"UNAUTHENTICATED","message":"账号或密码不正确。","requestId":"a91b…"}}
```

重复请求：登录不设幂等键；连续两次相同凭据 → 两次均 `200`，各自返回独立令牌（属预期行为，不是 `DUPLICATE_REQUEST`）。

### 4.4 API-04 座位状态查询（按自习室、按日）

| 项目 | 内容 |
| --- | --- |
| **接口编号/名称** | API-04 / 座位状态查询 |
| **需求与决策依据** | FR-04、FR-07（筛选）、C-7（状态计算优先级）、DD02（座位属性）、PS-01/NFR-08（学生看不到占用者身份）、KQ-06/PS-02（管理员范围） |

| **隐私** | 学生端 `state` 只表达"是否被占"，不暴露是谁、预约多久。NFR-08 明确"座位仅显示已占用"。 |

### 4.6 API-06 创建预约（核心写接口）

| 项目 | 内容 |
| --- | --- |
| **接口编号/名称** | API-06 / 创建预约 |
| **需求与决策依据** | FR-08、FR-13；BR-02（7 天窗）、BR-03（本人不重叠）、BR-04（座位不重叠）、BR-07 + F-8（黑名单）、BR-18/P-1（最多 2 个有效）、F-1/F-2/F-4、P-2；决策表 7.1 R1～R8；UC-01、UC-12、UC-13；ST-01、ST-08；ADR-002（整点网格）；ADR-1（账户停用先于黑名单判定） |
| **方法与路径** | `POST /api/v1/reservations` |
| **调用者及权限** | 仅 STU（F-3：不得替他人预约）。ADM 代约走 S2 的 UC-15 专用接口，**不复用本接口**（PS-04 要求留痕，字段不同）。黑名单用户可调用但必被拒（F-8）。 |
| **请求** | 请求头：`Idempotency-Key` 必填（§3.7）。请求体：`seatId` int 必填，>0；`startsAt` ISO-8601 必填，`minute==0 && second==0`（ADR-002），否则 `VALIDATION_FAILED`；`endsAt` ISO-8601 必填，整点且 **严格大于** `startsAt`。**允许跨小时**（Q-19 裁决 A）：跨度上限 = 该自习室当日剩余开放时长，且必须满足 `openHour <= startsAt 的整点` 与 `endsAt 的整点 <= closeHour`；`closeHour=24` 时 `endsAt` 写**次日 `T00:00:00`**（§3.1），跨日期但不算"跨开放边界"。跨开放时间边界（如 21:00–23:00 而 22:00 关门）返回 `RESERVATION_BLOCKED`（`rule="R-open"`）。空值规则：`null` 或不传均视为缺失；不接受的额外字段**忽略**（向前兼容）但记录到日志。 |
| **成功响应** | `201`，`Location: /api/v1/reservations/{id}`；`data`：`reservationId` int、`status` enum `BOOKED`、`seatId`、`seatLabel`、`roomId`、`roomName`、`startsAt`、`endsAt`、`checkInWindow`{`start`,`end`}、`activeReservationCount` int（创建后本人有效预约数）、`createdAt`。业务状态：待签到。`checkInWindow.end` 按**当前生效**规则版本计算（Q-30 裁决 A）。 |
| **失败响应** | 见下方"失败语义表"，逐条给出码、条件与数据是否改变。 |
| **前置与后置** | 前置状态：账号 `ACTIVE`、不在黑名单有效期内、目标座位 `state=AVAILABLE`（F-4）、自习室 `active=true`。后置不变量（全部须同时成立）：① 该座位 `[startsAt, endsAt)` 区间内**不存在**其他 `BOOKED`/`CHECKED_IN` 预约；② 本人同区间无重叠有效预约；③ 本人有效预约数 ≤ 2；④ 新增恰好 1 条预约记录，状态 `BOOKED`；⑤ 座位占用记录与预约记录一一对应（§5.3）。 |
| **并发与幂等** | 幂等键必需。**并发控制**：先按 §5.4 的固定锁顺序获取"座位占用"的排他锁，再做 ①②③ 的写入前复核，最后写入。竞争失败统一返回 `409 SLOT_TAKEN`（不是 500）；**锁等待超时**同样返回 `409 SLOT_TAKEN` 并带 `fields.reason="LOCK_TIMEOUT"`（Q-29 裁决 C），确实被占则 `fields.reason="OCCUPIED"`。同一用户的两个并发预约请求（不同座位）也要串行，否则 ③ 的计数会双计，为此**锁顺序第一位是"用户预约配额"**，见 §5.4。 |
| **事务** | 同一事务内必须成功：插入预约记录 + 插入座位占用记录（可能多条）+ 插入 `notification_outbox` 事件行（`event_type=RESERVATION_CREATED`）+ 幂等记录 + 写审计（若为代约则必写）。事务外副作用：outbox 投递（S2，S1 只写不投）；任何缓存失效操作必须在**事务提交后**执行，失败只记日志不回滚业务。 |
| **隐私** | 响应只含本人预约；不得返回该座位的其他预约信息（包括是否被他人预约）。日志不记完整请求体以外的个人字段。 |
| **测试关联** | TC-API06-01 正常；TC-API06-02 黑名单拦截；TC-API06-03 过去时间；TC-API06-04 超 7 天；TC-API06-05 座位停用；TC-API06-06 座位时段被占；TC-API06-07 本人时段重叠；TC-API06-08 已有 2 个有效预约；TC-API06-09 并发同座位同时段仅 1 成功；TC-API06-10 同幂等键重放只 1 条记录；TC-API06-11 非整点被拒；TC-API06-12 跨小时拆分原子性（失败时无残留时段记录）。对应 AV-01、AV-09（R1～R8）、AV-12、AV-14 前置。 |
| **确认** | 提供方：预约模块负责人（待填）；调用方：前端（待填）；复核人：（待填）；版本：v1.0-draft |

### 4.7 API-07 取消预约（核心写接口）

| 项目 | 内容 |
| --- | --- |
| **接口编号/名称** | API-07 / 取消预约 |
| **需求与决策依据** | FR-09、BR-05、F-5、P-4、决策表 7.2；UC-02；ST-02、ST-09；ADR-08（取消不限次）；PS-03（管理员不能直接改状态，代取消须留痕，S2） |
| **方法与路径** | `POST /api/v1/reservations/{id}/cancel` |
| **调用者及权限** | 预约本人（STU）。管理员代取消属 UC-15，S2 另接口。 |
| **请求** | 路径 `id` int 必填。请求头 `Idempotency-Key` 必填。请求体：`reason` string 可选，≤200 字符，仅本人取消时允许留空。 |
| **成功响应** | `200`；`data`：`reservationId`、`status` = `CANCELLED`、`cancelledAt`、`seatFreed` bool、`activeReservationCount`。业务状态：已取消。 |
| **失败响应** | ① 非本人 → `403 FORBIDDEN_OBJECT`；② 不存在 → `404`；③ 状态非 `BOOKED` → `409 RESERVATION_STATE_CONFLICT`（`currentStatus`），数据不变；④ 已过取消截止（`now > startsAt - cancelLeadMinutes`）→ `422 CANCEL_TOO_LATE`，`fields.cancelDeadline`，数据不变；⑤ 已被扫描任务判违约 → `409 RESERVATION_STATE_CONFLICT`（`currentStatus=VIOLATED`）。 |
| **前置与后置** | 前置：`status = BOOKED` 且 `now <= startsAt - cancelLeadMinutes`（**含等于**，即恰好提前 30 分钟仍可取消，Q-03 裁决 C；`cancelLeadMinutes` 默认 30，API-19 可调）。后置不变量：预约状态变 `CANCELLED`；**物理删除**该预约的全部座位占用记录（Q-02 裁决 B、§5.3 方案 A，释放整格、不计算剩余分钟）；该座位该时段重新对他人可约；**不产生**违约记录；本人有效预约数减 1。 |
| **并发与幂等** | 幂等键必需。并发：与扫描任务可能同时处理同一预约（扫描判违约 vs 用户取消），必须靠"状态条件的原子更新"决胜：`UPDATE reservation SET status='CANCELLED' WHERE id=? AND status='BOOKED'`，受影响行数 0 则返回 `RESERVATION_STATE_CONFLICT`。**不得**先查后改。 |
| **事务** | 同一事务：更新预约状态 → 删除占用记录 → 插入 `notification_outbox`（`event_type=RESERVATION_CANCELLED`）→ 写审计（取消行为属 FR-20 留痕范围）。事务外：outbox 投递（S2）。 |
| **隐私** | `reason` 在本人响应中原样返回；管理员侧 S2 接口才可见，且不外泄给学生他人。 |
| **测试关联** | TC-API07-01 正常；TC-API07-02 29 分钟被拒；TC-API07-03 恰好 30 分钟（依 Q-03 结论）；TC-API07-04 已签到状态被拒；TC-API07-05 他人取消 403；TC-API07-06 取消后他人可约（ST-09）；TC-API07-07 与扫描并发时只有一方成功；TC-API07-08 同键重放。对应 AV-02、AV-10。 |
| **确认** | 预约模块负责人；复核人（待填） |

**示例**

正常：
```http
POST /api/v1/reservations/9001/cancel
Idempotency-Key: 4c9d…   {"reason":"临时有课"}
→ 200 {"data":{"reservationId":9001,"status":"CANCELLED","cancelledAt":"2026-11-30T11:02:19",
        "seatFreed":true,"activeReservationCount":0},"meta":{"requestId":"…"}}
```

业务失败：
```http
→ 422 {"error":{"code":"CANCEL_TOO_LATE","message":"距预约开始不足 30 分钟，无法取消。",
 "fields":{"cancelDeadline":"2026-12-01T13:30:00"},"rule":"BR-05","requestId":"…"}}
```
数据断言：预约仍为 `BOOKED`，占用记录仍存在。

重复请求：
```http
同 Idempotency-Key 再发 → 200（重放首次响应，meta.replayed=true）
换新 Idempotency-Key 但对已取消的预约再发 → 409 RESERVATION_STATE_CONFLICT（currentStatus=CANCELLED）
```

### 4.8 API-08 签到（核心写接口）

| **成功响应** | `200`；`data`：`reservationId`、`status`=`CHECKED_IN`、`checkedInAt`、`seatState`=`IN_USE`、`checkOutDeadline`（= `endsAt`）。业务状态：使用中。 |

| **事务** | 同一事务：条件更新预约状态与 `checkedInAt` → 写审计（签到属行为记录，可审计）。事务外：无。 |
| **隐私** | 响应不含座位位置以外的他人信息。日志记 `reservationId` 与用户 ID。 |
| **测试关联** | TC-API08-01 正常；TC-API08-02 窗口前 1 分钟被拒；TC-API08-03 窗口后 1 分钟被拒；TC-API08-04 重复签到 `checkedInAt` 不变；TC-API08-05 他人/管理员 403；TC-API08-06 黑名单用户可签到；TC-API08-07 已被判违约后签到 409。对应 AV-01、AV-11、AV-06⑤。 |
| **确认** | 预约模块负责人 + 签到签退模块负责人 |

→ 200 {"data":{"reservationId":9001,"status":"CHECKED_IN","checkedInAt":"2026-12-01T14:03:12",

### 4.9 API-09 签退（核心写接口，含早退违约判定）

| 项目 | 内容 |
| --- | --- |
| **接口编号/名称** | API-09 / 签退 |
| **需求与决策依据** | FR-11、BR-09、BR-20（C-3 早退违约）、P-5（结束前完成签退）、决策表 7.3 R3/R4；UC-03 主流程 6～8 与替代流程 8a；ST-04、ST-11 |
| **方法与路径** | `POST /api/v1/reservations/{id}/check-out` |
| **调用者及权限** | 仅本人（STU）。ADM 不可代签退（F-6）。 |
| **请求** | 路径 `id`；`Idempotency-Key` 必填；无请求体。 |
| **成功响应** | `200`；`data`：`reservationId`、`status`=`COMPLETED`、`checkedOutAt`、`early` bool（是否触发早退）、`violationCreated` bool、`violationId` int 或 null、`seatFreedFrom` ISO-8601 或 null（**被删除的最小 `slot_start`**；无后续整点可释放时为 null）。业务状态：已完成。 |
| **失败响应** | ① 状态非 `CHECKED_IN` → `409 RESERVATION_STATE_CONFLICT`；② `now > endsAt` → `422 CHECKOUT_NOT_ALLOWED`（超时应由扫描任务判 C-2，不由签退接口兜底），数据不变；③ 非本人 → `403 FORBIDDEN_OBJECT`。 |
| **前置与后置** | 前置：`status=CHECKED_IN`；`now <= endsAt`。后置不变量：预约 `COMPLETED`；若 `now < endsAt - earlyLeaveThresholdMinutes`（**不含等于**，恰好提前 30 分钟不记，Q-03 裁决 C）则**必须**同时新增 1 条 `EARLY_LEAVE` 违约记录并计 1 分（BR-20、C-3、决策表 R3）；**释放后续整点时段**：删除 `slot_start > now` 的占用记录，当前所在整点不释放（Q-05 裁决 B）；该预约结束后的评价资格成立（S2 用）。 |
| **并发与幂等** | 幂等键 + 状态条件更新。与扫描任务（C-2 超时未签退）竞争：用户在 `endsAt+1min` 才签退、但扫描已在 `endsAt+15min` 后判违约，则签退遇 `409`；若扫描尚未运行，签退先成功，则扫描不得再对该预约判 C-2（见 §5.6 幂等条件）。 |
| **事务** | 同一事务：条件更新预约状态 → 删除后续整点占用（Q-05）→ 必要时插入违约记录 → 更新学期违约分 → 判断是否触发黑名单（ST-13）→ 插入 `notification_outbox`（`event_type=RESERVATION_COMPLETED`，若早退另插 `VIOLATION_CREATED`）→ 幂等记录 → 写审计。黑名单判定见 §5.5；**该判定必须在同一事务**，否则会出现"违约已记、黑名单未进"，扫描补偿能救但会增加复杂度。 |
| **隐私** | 响应只含本人。违约原因文案不含管理员身份信息（早退为系统判定）。 |
| **测试关联** | TC-API09-01 正常签退；TC-API09-02 早退 ≥30 分钟 → 1 条 `EARLY_LEAVE`；TC-API09-03 恰好提前 30 分钟整签退 → **不记违约**（`now < endsAt-30min` 为假，Q-03 裁决 C），29:59 → 记违约；TC-API09-04 结束时间后签退 → `CHECKOUT_NOT_ALLOWED`；TC-API09-05 未签到状态 → 409；TC-API09-06 与扫描并发仅一方成功；TC-API09-07 重复签退幂等；TC-API09-08 跨小时预约 14:30 签退释放 15–16 格（`seatFreedFrom=15:00`）且他人可约。对应 AV-04b、AV-01。 |
| **确认** | 预约模块负责人 + 违约/黑名单模块负责人 |

**示例**

正常（早退）：
```http
POST /api/v1/reservations/9001/check-out
Idempotency-Key: 93ab…
→ 200 {"data":{"reservationId":9001,"status":"COMPLETED","checkedOutAt":"2026-12-01T15:10:00",
        "early":true,"violationCreated":true,"violationId":5011,
        "seatFreedFrom":null},"meta":{"requestId":"…"}}
```
> `seatFreedFrom` 的取值受 Q-05 裁决 B 约束：**只释放后续整点时段，不释放当前所在整点**（ADR-002 不支持碎片）。例：14:00–16:00 的预约在 **14:30** 签退 → 删除 15:00–16:00 的占用、`seatFreedFrom="…T15:00:00"`；在 **15:10** 签退 → 15:00–16:00 已在使用中，无格可删、`seatFreedFrom=null`。单小时预约（如 15:00–16:00）签退时恒为 `null`。

业务失败：
```http
→ 422 {"error":{"code":"CHECKOUT_NOT_ALLOWED","message":"已超过预约结束时间，系统将判定违约。",
 "fields":{"endsAt":"2026-12-01T16:00:00"},"rule":"C-2","requestId":"…"}}
```

重复请求：
```http
同键重放 → 200（replayed=true），违约记录仍只有 1 条（按 reservationId 唯一，见 §5.3）
换新键再签退 → 409 RESERVATION_STATE_CONFLICT（currentStatus=COMPLETED）
```

> 本章只写"靠猜就会出错"的部分：状态转换、唯一约束、锁顺序、事务边界、超时重试、异常恢复、规则版本。凡需求已写清、实现直观的部分（如列表查询）不在此重复。

### 5.1 状态转换表

#### 5.1.1 预约单状态（ST-01～ST-07）——接口级可执行版

> ✅ **Q-12（裁决 A）**：ADR-2 要求"已签到用户收到提示且签到被取消"，但 GM-07 与 ST 表没有"`CHECKED_IN` → 某终止态"这条转换，终态集合（DD05）也没有"已终止"。采用**以 `COMPLETED` 为落点 + `terminatedBy` 标记**（取值 `SEAT_DISABLED`/`ROOM_DISABLED`/`null`），不引入新状态、不破坏 DD05。**连带口径**：任何"完成率"统计必须排除 `terminatedBy IS NOT NULL` 的记录（已写入 §6.3）。

> 座位状态只有**一个**权威字段 `Seat.state`（生命周期视角）。"某座位某时段是否空闲"**不落字段**，由 C-7 实时计算（§5.1.3）。这一点必须显式写下来，否则不同实现者会各自加一个 `seat.occupied` 布尔值，导致状态不一致。
>
> ✅ **Q-07（裁决 B）：维护中与停用语义不同**。`MAINTENANCE` 表达"短期不可用但计划内的预约仍有效"（如换桌垫、临时维修）；`DISABLED` 表达"长期不可用，需要把已有预约清掉"（如座椅报废）。二者的差别**只在是否取消未来预约、是否终止使用中预约**，在"是否可被新预约"上完全一致（都不可约）。若实现简化成等价处理，`MAINTENANCE` 的场景会误伤已排好的预约，属验收失败。

#### 5.1.3 座位"时段状态"的计算（C-7 的可执行定义）

```
for a given (seat, instant t):
  if seat.state == DISABLED                        -> DISABLED
  else if seat.state == MAINTENANCE                -> MAINTENANCE
  else if exists reservation r on seat with
          r.status = CHECKED_IN
          and r.startsAt <= t < r.endsAt           -> IN_USE
  else if exists reservation r on seat with
          r.status = BOOKED
          and r.startsAt <= t < r.endsAt           -> BOOKED      ← 有有效预约即已约，无 15 分钟前置
  else                                             -> AVAILABLE
```

> **与 C-7 原文的差异（Q-27 裁决 B）**：C-7 原文写"已预约（当前时刻落在未开始预约区间内，且**距开始 < 15 分钟**）"。本契约**删除该 15 分钟限定**：只要有覆盖该时刻的有效 `BOOKED` 预约就显示 `BOOKED`。
>
> **理由**：C-7 字面与 UC-01 验收 ⑤ / AV-12"其他学生查询该时段时看不到该座位"直接冲突。若按字面，明天 14:00 的预约在今天查询时显示"可用"，学生会点进去再被拒，体验与验收都无法通过。
>
> **正确性说明**：即使按字面显示"可用"，提交 API-06 仍会被 U-1 唯一约束挡住返回 `409 SLOT_TAKEN`，因此**无论采用哪种解释都不会出现双占**；本条只影响"看到的状态"这一验收措辞。
>
> **需同步**：C-7 在《需求规格说明书》中加注"『已预约』指存在覆盖该时刻的有效预约，不采用『距开始 <15 分钟』限定"（需需求文档维护人会签，见 §7.4）。

### 5.2 创建预约的校验链与拆分规则

**校验链顺序（与决策表 7.1 一一对应，命中即停，不在同一请求内继续检查后续项）**

1. 认证（§3.3 步骤 1）→ 2. 账号状态（步骤 2）→ 3. 角色 STU（步骤 3）
4. 字段格式：整点、`endsAt>startsAt`、`endsAt 的整点 <= closeHour`、跨度 ≤ 房间当日余量（`VALIDATION_FAILED`）
5. 黑名单（`BLACKLISTED`）→ 6. `startsAt < now`（R2）→ 7. 超 7 天（R8）→ 8. 座位生命周期（R3）→ 9. 房间停用 → 10. 开放时间（BR-02）
11. **进入临界区**：锁（§5.4）→ 12. 座位占用（R4，`SLOT_TAKEN`）→ 13. 本人重叠（R5）→ 14. 本人有效预约数（R6）→ 15. 写入

> 5～10 在锁外（可并发执行，只读，用于快速失败）；12～14 在锁内（权威判定）。**顺序不可交换**：若把 R6 放在 R4 之前，用户 A 已有 2 个预约去抢一个被占的座位，会得到"额度已满"而不是"已被占用"，与 AV-09 的逐列构造相冲突（AV-09 要求每条规则单独构造时可判定）。

**跨小时预约的拆分（ADR-002）**

- 请求 `14:00–16:00` → 拆为 `(14:00,15:00)`、`(15:00,16:00)` 两条占用记录 + 1 条预约记录。
- 写入是**一个事务**：任一占用记录插入失败（唯一约束冲突）→ 整个事务回滚 → 返回 `SLOT_TAKEN`。断言：失败后占用表无任何残留行（TC-API06-12）。
- 预约记录本身**不含**时段拆分字段；拆分只在占用表体现。这样取消/违约时只需按 `reservationId` 删除/失效占用记录，不必反算。
- 若实现改为"预约表也存多个时段行"，则必须保证两表拆分完全一致，属于实现自由但不推荐（增加一致性维护点）。

**"释放"的统一口径（Q-02 / Q-05 裁决后）**

| 触发 | 删除范围 | `seatFreedFrom` |
| --- | --- | --- |
| 取消（API-07） | 该预约的**全部**占用记录 | 不适用（响应 `seatFreed` bool） |
| 自动违约（ST-05/05a）、手动违约（API-16） | 该预约的**全部**占用记录 | 不适用 |
| 停用联动取消（ST-02'） | 该预约的**全部**占用记录 | 不适用 |
| 正常签退（API-09） | 仅 `slot_start > now` 的**后续**整点记录 | 被删的最小 `slot_start`；无则 `null` |

> 关键区分：取消/违约是"这个预约不再成立"，所以整段释放；签退是"人提前走了"，当前这一小时仍算用过，只释放后续整点。**不得**对签退做"删全部"，否则同一小时会出现"刚用过就被别人约"的重复计费/冲突争议。
>
> ⚠️ **与 F-5 / 决策表 7.2 R2 的关系（须在需求侧处理）**：在 Q-03 裁决 C 的取消截止（`now <= startsAt - cancelLeadMinutes`）下，**"开始后 15 分钟内取消"在契约上不可能发生**——API-07 在 `startsAt` 之前 30 分钟就关闸了。因此 F-5 与决策表 7.2 R2 的那一句要么删除、要么改为"若将来放开开始后取消，按本节释放规则删整格"。本版按"契约不允许开始后取消"实现（见 §6.2 C-8）。

**U-1 与 U-8 的落地写法（Q-28 裁决 C：SQLite 3.45）**

- **选型与代价**：SQLite 零部署、课程环境最省，**但没有行锁**，并发正确性只能靠 `BEGIN IMMEDIATE`（全局写锁）串行化（§5.4）。因此本系统中的"并发测试"验证的是"应用层串行 + 唯一约束"，不是真实行锁竞争；迁移到 PostgreSQL/MySQL 时 **U-1/U-8 的写法与锁实现都必须重做**（已在 §5.9 列为迁移红线）。
- **U-1 不需要部分索引**：§5.3 已定"方案 A：占用记录只表达当前有效占用，取消即删除"，所以表中不存在"失效行"，普通唯一约束即可。
- **U-8 需要部分唯一**：`now()` 不能进入索引谓词（SQLite 要求确定性表达式），因此采用下面的组合——"部分索引 + 写前关闭已过期行"。读路径仍按 `blacklist_until > now()` 判定（ST-14a 不变）。

```sql
-- U-1：座位占用唯一（跨小时拆分后每格一行）
CREATE UNIQUE INDEX IF NOT EXISTS u1_occupancy
  ON seat_occupancy(seat_id, slot_start);

-- U-8：同一用户至多一条"未关闭"的黑名单记录
CREATE UNIQUE INDEX IF NOT EXISTS u8_blacklist_active
  ON blacklist(user_id) WHERE released_at IS NULL;

-- 写路径（创建黑名单前，同一事务内执行）：
-- 把已到期但尚未关闭的记录关掉，避免 U-8 误挡新建
UPDATE blacklist
   SET released_at = blacklist_until
 WHERE user_id = :uid AND released_at IS NULL AND blacklist_until <= :now;
```

| 未来迁移目标 | U-8 等价写法 |
| --- | --- |
| PostgreSQL | 同上 `CREATE UNIQUE INDEX ... WHERE released_at IS NULL`（原生支持部分索引） |
| MySQL 8 | 生成列 `active_user AS (IF(released_at IS NULL, user_id, NULL))` + `UNIQUE(active_user)`（MySQL 允许多个 NULL） |

**占用记录"删除还是标记失效"（v1.1 已定：删除）**

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| A. 取消时**删除**占用记录 | 唯一约束语义简单；不存在"历史占用" | 丢失"该时段曾被约"的历史（由预约表本身保留，可接受） | **推荐** |
| B. 标记 `released_at` | 可审计 | 唯一约束必须改为部分索引；查询都要加条件，易漏 | 不推荐 |

> 本文档采用方案 A（**由 Q-02 裁决 B 确认**）：**占用记录只表达"当前有效占用"**，历史完全由 `reservation` 表承担。所有释放动作（取消、自动违约、手动违约、停用联动）都删除对应占用记录；签退只删后续整点（Q-05）。§4.7 后置不变量已直接写为"物理删除"，不再保留二选一。

### 5.4 锁顺序（并发正确性的核心）

**目标**：① 同一座位同一时段不可能双占；② 同一用户有效预约数不会超过上限；③ 不发生死锁。

**锁的层级与全局顺序（任何事务都必须按此顺序获取，不得逆序）**

```
L1  user_quota(user_id)         ← 用户预约配额锁
L2  seat(seat_id)               ← 座位行锁
L3  reservation(reservation_id) ← 预约行锁
L4  idempotency(scope, key)     ← 幂等键登记
```

| 接口 | 获取顺序 | 说明 |
| --- | --- | --- |
| API-06 | L4 → L1 → L2 | 先登记幂等（防重复），再锁用户（防额度双计），最后锁座位（防双占）。**L1 在 L2 之前**：若先锁座位再锁用户，两个用户互锁对方额度（A 锁座位 S 等用户锁，B 锁用户等座位 S）即死锁 |
| API-07 | L4 → L3 → L2 | 锁预约行后删除占用（需锁座位行以保持与 API-06 相同的资源顺序） |
| API-08 | L4 → L3 | 只改预约状态，不碰座位行（座位状态是派生的） |
| API-09 | L4 → L3 → L1 | 可能触发黑名单与计分，需锁用户额度/计分行（与 API-16 顺序一致） |
| API-13d | L4 → L2 → L3* | 先锁座位，再逐个锁该座位的预约（`ORDER BY reservation_id` 固定的加锁顺序，避免批量锁乱序死锁） |
| API-13b | L4 → L2(room) → L3* | 先锁自习室，再按 `ORDER BY reservation_id` 逐个锁该室座位的预约（取消 + 终止） |
| API-16 | L4 → L3 → L1 | 与 API-09 一致 |
| API-18b | L4 → L1(user) → L3* | 改账号状态 + 取消其未来预约，需再锁预约行（§5.7） |
| API-19 | L4 → L7(rule_parameter) | 乐观锁，不参与上述层级（版本号冲突即重试） |

> **L1/L2 的落地（Q-28 裁决 C：SQLite）**：SQLite 无行锁，本实现**不使用** `SELECT ... FOR UPDATE`。所有写事务一律用 `BEGIN IMMEDIATE` 开启：它在事务开始即获取数据库级写锁，等价于"全局串行化"，因此 L1→L2→L3 的逻辑顺序在代码中仍须保持（便于未来迁移与阅读），但物理上不会出现交错，也不会死锁。
>
> **代价与红线**：① 并发写被完全串行，吞吐上限由写事务时长决定——单条写事务须控制在毫秒级（禁止在事务内做循环查询、禁止调用外部服务，§5.7 已规定）；② 并发测试只能验证"在串行化下不变量成立"，**不能**声称验证了行级锁竞争；③ 迁移到 PostgreSQL/MySQL 时，必须按上表重做 `FOR UPDATE` 锁实现并重跑全部并发用例。
>
> **锁等待超时（Q-29 裁决 C）**：SQLite 的 `busy_timeout` 默认 5 秒（可配置 `dbBusyTimeoutMs`）；超时后返回 `409 SLOT_TAKEN` 并带 `fields.reason="LOCK_TIMEOUT"`（区别于确实被占的 `OCCUPIED`），写审计 `code=LOCK_TIMEOUT`。**不采用 425 Too Early**：本系统前端不自动重试，避免"重试成功但用户已换座"的困惑。

**死锁预防与观测**
- 唯一规则：**所有写事务的加锁顺序必须与上表一致**；新增写接口必须先在本表登记再实现。
- 若仍出现死锁（数据库报告），处理为：回滚 → 记审计（`code=DEADLOCK`）→ 返回 `409 SLOT_TAKEN`。**不得**自动无限重试。

### 5.5 违约计分与黑名单判定（规则版本化）

**计算口径（须与 C-5/C-6 逐字对齐）**

```
termStart        = 当前生效参数 semesterStart（date）
termScore(u)     = COUNT(violation WHERE user_id = u AND created_at >= termStart
                         AND waived_at IS NULL)
n(u)             = COUNT(blacklist WHERE user_id = u AND created_at >= termStart
                         AND revoked_at IS NULL)     ← 本自然学期已生效且未撤销的进入次数
blacklistDays(n) = MIN(blacklistDaysPerEntry × n, blacklistMaxDays)
```

> **不设 `termEnd`**：学期滚动由"调整 `semesterStart`"形成自然边界，查询一律 `created_at >= termStart` 即可。历史学期分数用"当时的 `semesterStart` 版本 + 区间记录"重建（`semesterStart` 的每次变更都在 `rule_parameter` 历史中留痕）。这样避免一个悬空的"下学期开始日"变量在实现时被随意填值。

| 决策点 | **v1.1 已定口径** | 依据 | 影响 |
| --- | --- | --- | --- |
| `n` 的含义 | 本自然学期内已生效的进入次数；`semesterStart` 变更（新学期开始）时清零为 0 | Q-08 裁决 A | 限制期长度；第 1/2/3/4/5 次分别为 7/14/21/28/30 天（封顶 30） |
| 期满后再进名单 | 学期分仍 ≥ 阈值即**立即**再进，`n` +1 | Q-08 裁决 A | 会出现"期满次日再进 14 天"，属设计意图 |
| 正在限制期内再违约 | `n` 不变，`until = MAX(until, now + blacklistDays(n))`；**不新建第二条记录**；仍受 `blacklistMaxDays` 封顶；仍写一条新违约记录 | Q-09 裁决 A | 余期不足时补足，余期较长时不缩短 |
| 申诉推翻后回退 | 置 `waived_at`（**不物理删除**，F-10）；重算 `termScore`；若 `< violationScoreThreshold` 且当前黑名单由该次触发 → `until = now`、置 `revoked_at`；被撤销的进入记录因 `revoked_at IS NOT NULL` **自动不再计入 `n`**（等价于"`n` 回退 1"）；写审计 `BLACKLIST_REVOKED` | Q-10 裁决 A | S2 实现；S1 只建列不用 |
| 学期清零 | 单一参数 `semesterStart`；每学期开学第一周内由 ADM 通过 API-19 调整（`reason` 写"2026 秋季学期开始"）；**任何读路径**都按当前 `semesterStart` 实时计算，不依赖清零任务 | Q-11 裁决 A | 参数漏改时分数不会自动清零——**已知限制**，通过 API-12 返回 `termStart` 让学生自查 |
| 历史分数是否可查 | 是：依 `rule_parameter` 版本历史 + 违约记录（含 `waived_at`）可重建任一学期 | Q-11 | S2 申诉与统计需要 |

> ⚠️ **已知限制（须写入验收说明）**：`semesterStart` 是全局单值。若管理员忘记在开学时调整，全校学生的学期分不会归零，会持续累加到调整为止。缓解：API-12 的 `termStart` 字段 + 前端提示"本学期自 YYYY-MM-DD 起计分"；运维侧在学期初提醒。

> **设计红线**：`termScore` 与 `blacklistDays` 的计算**只能有一处实现**（一个领域服务），API-12 的展示、API-06 的拦截、API-16 的判定必须调用同一函数。否则会出现"页面显示 2 分、实际已被拦"的自相矛盾。
>
> **规则版本**：每次计分/判定都必须记录当时生效的参数版本号（`ruleVersion`），写入违约记录或黑名单记录的 `rule_snapshot` 字段。这样在参数调整后，能回答"这条违约当时是按什么规则判的"（NFR-12、§8.3 "调整留痕"）。

### 5.6 定时任务：幂等、漏跑补偿与恢复

| 任务 | 周期（ADR-7） | 查询条件（须走 I-3 索引） | 单条处理动作 | 幂等条件 |
| --- | --- | --- | --- | --- |
| T-1 超时未签到 | 1 分钟 | `status='BOOKED' AND starts_at + checkInWindow < now` | ST-05：`BOOKED→VIOLATED`、写 `NO_SHOW`、删除全部占用、计分、黑名单 | 状态条件更新 + U-2 |
| T-2 超时未签退 | 1 分钟 | `status='CHECKED_IN' AND ends_at + noCheckoutGrace < now` | ST-05a：`CHECKED_IN→VIOLATED`、写 `NO_CHECKOUT`、删除全部占用、计分、黑名单 | 同上 |
| T-3 黑名单期满 | 每小时 | `blacklist_until <= now AND released_at IS NULL` | 写 `released_at` + outbox（S2 投递） | 更新条件带 `released_at IS NULL` |
| T-4 学期初提醒 | 每天一次（可选） | 当前日期与 `semesterStart` 同月且距今 > 180 天 | 写一条运维告警"疑似未调整 semesterStart"，**不自动改参数** | 告警去重键（`semesterStart` + 日期） |

> **T-4 的定位变化（Q-11 裁决 A）**：学期清零**不再由任务改参数**，改由 ADM 每学期开学第一周内通过 API-19 调整 `semesterStart`（有审计、有 `reason` 四项约束）。任务角色降级为"提醒"，避免"任务自动推进参数但无人复核"的隐性风险。
>
> **判定表达式红线（Q-18 裁决 A）**：所有扫描与判定的时间比较**只能**写成"表字段 vs `now()`"，**不得**使用进程内缓存的相对时间或上次执行时刻。这样测试直接改 `starts_at`/`ends_at` 即可构造场景（§3.8 已列允许修改的字段清单），且停机后补跑结果与正常跑一致。

**批处理事务粒度（必须明确）**

| 方案 | 风险 | 结论 |
| --- | --- | --- |
| 整个批次一个事务 | 一条失败整批回滚，循环重试不收敛（单条数据本身非法时永远卡住） | 不采用 |
| 每批 N 条一个事务 | 部分成功，需记录断点 | 可选（N=100） |
| **每条一个事务** | 事务数多，但失败隔离最好，且幂等由 U-2 兜底 | **采用** |

- 每个条目独立事务，单条失败只记审计与告警，**不中断**整个批次；批次结束后报告 `scanned / succeeded / failed`。
- **补偿（ADR-7 启动补偿）**：应用启动时立即执行一次全部任务，且**不受周期限制**（因为条件查询天然幂等）。补偿执行与常规执行可以重叠，结果仍一致——这正是"用状态条件而不是用"已处理"标记"的原因。
- **漏跑多久都要能补**：查询条件只用"时间比较"，不依赖"上次执行时间"。因此停机 3 天后启动，一次扫描即可补齐所有应判违约的预约（AV-03 构造式测试即依赖这一点）。
- **每次扫描写入 `scan_run`（开始/结束/耗时/计数）**，供 API-20 指标与 UC-14 的失败 3 次告警（NFR-05）。
- **超时**：单条处理超过 5 秒记慢查询并继续下一条；整批超过 5 分钟自动中止并告警（避免长事务阻塞预约写入）。

**与用户请求的竞争**（必须显式写清，否则两边都会"兜底"导致重复）

> ✅ **Q-31（裁决 A）**：决策表 7.3 R5"以手动登记为准"解释为**先到者胜**——谁先提交成功，另一方收到 `409`；**不允许**手动覆盖已存在的自动违约记录（会违反 U-2 与 F-10）。两种 409 语义须区分：状态已变 → `RESERVATION_STATE_CONFLICT`；状态未变但已有记录 → `DUPLICATE_VIOLATION`。

| 竞争 | 结果 |
| --- | --- |
| 用户签到 vs T-1 判违约 | 以 `status` 条件更新为例，谁先改谁赢；输的一方得到 `409`/`failed`，**不产生第二条违约** |
| 用户签退 vs T-2 | 同上 |
| 管理员登记违约 vs T-2 | 同上 |
| 用户取消 vs T-1 | 同上（取消在 `startsAt-30min` 前，理论上早于 T-1；但测试数据可构造重叠） |

> 现状提醒：原型代码把扫描挂在 `before_request`（每个请求都跑一遍全表查询），既不符合 ADR-7 的"定时任务"，也是性能隐患。这属于 §6 的实现差异，本文档在 §5.9 给出迁移口径。

### 5.7 事务边界速查表

| 接口 | 必须同时成功的写入 | 事务外（失败不回滚业务） |
| --- | --- | --- |
| API-06 | 预约 + 占用(N) + outbox + 幂等记录 + 审计（若代约） | outbox 投递、缓存失效、指标 |
| API-07 | 预约状态 + 删除占用(N) + outbox + 幂等记录 + 审计 | outbox 投递 |
| API-08 | 预约状态 + `checkedInAt` + 幂等记录 + 审计 | — |
| API-09 | 预约状态 + 删除后续占用(N) + 违约(0/1) + 学期分 + 黑名单(0/1) + outbox + 幂等记录 + 审计 | outbox 投递 |
| API-13a/c | 资源行 + 幂等记录 + 审计 | — |
| API-13b | 自习室 + 取消的预约(N) + 终止的预约(N) + 删除占用(N) + outbox(N) + 审计(N) | outbox 投递 |
| API-13d | 座位 +（仅 `DISABLED`）取消的预约(N) + 终止的预约(N) + 删除占用(N) + outbox(N) + 审计 | outbox 投递 |
| API-16 | 违约 + 预约状态 + 删除占用 + 学期分 + 黑名单(0/1) + outbox + 幂等记录 + 审计 | outbox 投递、缓存失效 |
| API-18b | 用户状态 + 取消的预约(N) + 终止的预约(M) + 删除占用(N+M) + outbox(N+M) + 幂等记录 + 审计 | outbox 投递 |
| API-19 | 新参数版本 + 旧版本关闭 + 幂等记录 + 审计 | 指标 |

**通用规则**
1. 审计**在业务事务内**写：因为"操作没成功就不该有成功审计"，而"操作成功但没有审计"违反 NFR-06。二者只能同成同败。
2. 缓存失效**在提交后**：提交后失效失败只记日志并留下"待失效"标记，由扫描兜底，**不回滚业务**（ADR-5：数据库是最终防线）。
3. 禁止在事务内调用外部服务（通知、邮件）。ADR-4 已定为仅站内通知；**S1 按 Q-13 裁决 B 只在事务内写 `notification_outbox` 行、不投递**；S2 由独立投递器消费 outbox，仍不得把投递动作放回业务事务。

### 5.8 规则参数版本与生效语义

| 项 | 约定 |
| --- | --- |
| 存储 | `rule_parameter(scope, version, params_json, effective_from, effective_to, created_by, reason)` |
| 读取 | 进程内**不得**缓存超过 5 秒；推荐每次校验时读"`effective_to IS NULL` 且 `effective_from <= now` 的最新版本" |
| 写入 | 乐观锁：`version` 必须等于当前最新版本；并发后到者 `409 RULE_PARAM_LOCKED` |
| 生效时点 | 从**新版本提交成功后**的下一次校验起 |
| 历史预约 | **不冻结版本、不回溯改写**：判定一律读"当前生效版本"；`appliesTo={fromNow:true, existingReservationsAffected:false}`（Q-26/Q-30 裁决 A） |
| 违约判定 | 一律用**判定时刻**的版本，并把快照写入违约记录 |
| 回滚 | 不做"删版本"，只能再发一个新版本回滚（保留全历史，NFR-06 精神） |

> ✅ **Q-26 ⇄ Q-30（合并裁决 A）**：**判定读当前版本，不冻结到预约**。
>
> - 语义澄清：`existingReservationsAffected=false` 的意思是"**不改写已存在预约的数据**"，**不是**"老预约仍按旧参数判定"。这两句话必须分开读，否则实现者会去找 `reservation.rule_version`。
> - 因此 S1 **不建** `reservation.rule_version` 列；T-1/T-2、API-07、API-09 取参统一调用 `rule_params.current()`。
> - 已知后果（须写入验收说明）：签到窗口 15→20 分钟后，昨天创建的预约今天也按 20 分钟判；"同类预约在不同日期受不同规则"是可接受的设计取舍。
> - 若将来业务要求"约定即合同"，改法见本节 §5.8 末"重新评估条件"。
>
> **重新评估条件**：出现因参数调整引发的学生申诉且业务认定"应按预约创建时规则执行"时，需新增 ADR 并加 `reservation.rule_version` 列（S2 前的破坏性变更，须升接口版本）。
