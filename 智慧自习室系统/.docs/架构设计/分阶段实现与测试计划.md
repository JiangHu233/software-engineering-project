- 测试案例：`TC-APIxx-nn`（接口层）、`TC-DB-nn`（数据库集成）、`TC-E2E-nn`（端到端）、`TC-PERF-nn`（性能）、`TC-UNIT-nn`（单元）。与《接口说明书》各接口"测试关联"行的占位编号一一对应。

### 1.3 三条硬规则（来自《操作指引》步骤 5）

1. **并发不变量必须用真实数据库多连接验证**。同一个进程里的顺序调用、内存 Mock、或用 `threading` 共享同一 `Session` 的测试，都不能证明并发正确（SQLite 文件库 + 每线程独立连接是课程条件下可接受的最低标准，见 §4.1）。
2. **外部模拟测试不能声称真实校园服务集成通过**。本期不对接 CAS/OAuth（ADR-12）、不发邮件短信（ADR-4），因此**不允许**出现"统一认证对接通过""通知渠道联调通过"的表述。
3. **测试失败先判责，再改代码**：实现不符 → 修实现；预期错误 → 须有依据与人工批准后修测试；需求冲突 → 重开 Q。禁止为"全绿"删断言。

## 3. 测试案例（模板 E）

### 3.0 阅读方式与两个特殊情况

- 每条案例按模板 E 的 9 个字段给出。`依据` 列说明预期结果来自哪一级依据（§1.1），凡标 `AI推导` 者**未经人工确认不得用于判责**。
- **S0 的案例是"元测试"**：它们不验证业务，而是验证"测试工具本身能否证明问题"。判断标准很直接——工具必须能在**当前实现**上失败（复现真实缺陷），否则工具无效。
- **执行结果列的现状**：本节填写的是 2026-11-26 由 AI 在本机实测的结果，标记为 `AI 实测`。AI 实测只能作为**开发前参考**，不能当作验收证据（验收证据须由测试责任人在固定环境重跑，见 §4.4）。凡 `未确认` 的预期，执行结果一律填 `阻塞（待预期确认）`。
- 本机上 `qa_checks/` 五个脚本是**检查过程中为复现问题临时写的**，不是项目代码（其自带说明已如此声明）。其中能被本文档吸收为正式案例的只有 3 条（§3.1），其余仅作为缺陷证据。

### 3.1 S0：测试工具与数据（元测试）

#### TC-DB-01 并发双占复现（真实数据库多连接）

| 字段 | 内容 |
| --- | --- |
| **编号/关联依据** | TC-DB-01；依据 L2（BR-04、FR-13、NFR-13）+ L3（ADR-002）+ L4（API-06）；AV-12 |
| **层级** | 数据库集成 |
| **场景和风险** | 两名学生对同一座位同一整点时段同时提交预约。风险：应用层"先查后写"在并发下双双通过，产生双占，直接违反 NFR-13/BR-04 |
| **前置数据与角色** | 合成数据：1 个自习室、1 个座位、2 个学生账号（`stu_a`/`stu_b`）。使用**真实数据库文件**（非内存库），每个线程持有**独立连接** |
| **操作/输入** | 用 2 个线程 + 2 个独立连接，通过 `threading.Barrier` 对齐到同一时刻，各自执行"插入同座位同时段预约"（S0 阶段直接对数据库写入；S1 阶段改为调用 API-06） |
| **预期结果** | 预约表只有 1 条该时段的有效记录；另一方的操作**必须**失败并返回明确原因；数据库无部分写入（占用表条数与成功预约数一致） |
| **预期确认人** | 测试责任人（占位），日期 待填 |
| **执行结果** | **AI 实测：同进程未复现双占，多进程双占已复现（缺陷）**。① 同进程（2 线程 + 独立 `test_client` + Barrier，5 轮）：每轮仅 1 条成功，数据库始终 1 条；② **多进程**（2 个独立进程各持有自己的 SQLite 连接，各自 `BEGIN IMMEDIATE` 后插入同一座位同一时段，3 轮）：**每轮两个进程都提交成功**，数据库中该时段出现 2 条有效预约。原因：`BEGIN IMMEDIATE` 只串行化了同一连接池/进程内的写入，跨进程时先提交者释放写锁后，后提交者的"占用检查"已无法回滚前者的结果——**当前实现没有任何数据库层唯一约束兜底**（见《接口说明书》§5.9 D-3），因此 `success=1` 只是单进程巧合，不是不变量 |
| **证据** | `evidence/TASK-S0-01/<日期>-db01-concurrency.log`。本次实测记录（2026-11-26，Python 3.14.0 / Flask 3.1.3 / SQLAlchemy via Flask-SQLAlchemy 3.x / SQLite 文件库）：<br>`round 1..5: ['ok','fail'] db_bookings=1`<br>`多进程 0: A committed|B committed`<br>`多进程 1: A committed|B committed`<br>`多进程 2: A committed|B committed`<br>⚠️ 本次实测为一次性探针脚本，未入库；正式证据须由 TASK-S0-01 交付可重复的 `harness` 脚本并重跑 |

> **这条案例的教训（必须写进预期）**：并发不变量要证明三件事——① 结构上不可能双占（唯一约束）；② 应用层在冲突时给出正确语义（`409` 而非 500、不吞异常）；③ **在有多个连接/进程时依然成立**。只测"单进程内结果只有 1 条"会给出虚假的安全感——本次实测正是如此。
>
> **本次实测的两个副作用（须知悉）**：① 探针脚本未指向临时库，而是按 `create_app()` 默认配置连到了 `instance/studyroom.db` 演示库，写入了 6 行重复预约；已按备份还原（`/tmp/studyroom.db.mutated_by_probe.bak`，删除 6 行后仅剩原有 1 行 `completed`）。② 这恰好说明 §4.1"测试必须隔离数据库"的要求是硬性的——下一节把该要求写成工具级约束。

### 4.2 并发验证工具（这是 S0 的核心交付物）

**为什么需要专门的工具**：本轮实测证明了"同进程看不出问题、多进程才暴露"（TC-DB-01）。因此 harness 必须满足：

| 要求 | 具体做法 | 断言内容 |
| --- | --- | --- |
| 真实数据库 | 文件库（非 `:memory:`） | — |
| **多连接** | 每个工作线程独立 `Session`/连接 | 连接 ID 在日志中可见 |
| **多进程（必须）** | 至少验证一次 `subprocess`/`multiprocessing` 两进程并发写同一座位时段 | 每轮"成功提交数 == 1" |
| 时序对齐 | `threading.Barrier(N)` 或进程间同步文件 | 确保真正并发，而非排队 |
| 每轮隔离 | 每轮用**新座位**或清库 | 避免上一轮残留导致假失败 |
| 可重复 | 轮数参数化（默认 50），失败时打印该轮的全部响应 | 结论可复核 |
| **不得用 Mock 代替数据库** | 禁止 `unittest.mock` 替换 `db.session` | — |
| 断言"失败语义" | 除"只有 1 条成功"外，还要断言失败方拿到冲突类错误码 | 防止"吞异常"式通过 |

### 4.3 时间与外部依赖

| 项 | 约定 |
| --- | --- |
| 时间构造 | 允许**改数据库中的时间字段**（AV-01 验收口径明确允许）；**禁止**改服务器系统时间（AS-03）❓Q-18 待确认构造范围 |

### 5.3 任务卡使用规则

| 规则 | 说明 |
| --- | --- |
| 编码前先建卡 | 没有任务卡的编码不进审查队列；与《操作指引》"学生核对计划后批准一个小任务"一致 |
| 一人一范围 | 同一文件的修改只能在**一个**在途任务里发生，避免两个 AI 任务同时改同一文件 |
| 停止条件优先 | 触发"停止条件"时必须停下来反馈，不得自行扩大范围改需求/接口/架构 |
| 完成标准四件套 | 代码 + 测试证据 + 文档更新 + 人工审查，缺一不得标"已完成" |
| 审查人不得是起草人 | 至少换一人看 diff（《操作指引》§五"关键变更由另一成员复核"） |
