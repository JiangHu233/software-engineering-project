# 验收与验证

> 应能够查到的内容：验收场景、来源核对、原型走查、覆盖和一致性检查
> 推荐表示形式：验收表、验证记录、追踪矩阵

本章节依据《需求分析》的用户故事（US-01～US-25）、功能清单（FR-01～FR-35）、用例（UC-01～UC-15）、规则（BR/P/F/C 系列）与状态转换（ST-01～ST-14）编写，回答四个问题：

1. **验收场景**——系统交付时按什么场景逐条检验（§1）；
2. **来源核对**——任务原文 7 条核心功能是否条条有归宿（§2）；
3. **原型走查**——界面原型/页面流是否覆盖核心业务闭环与异常提示（§3）；
4. **覆盖和一致性检查**——需求、规则、状态、用例、验收项之间是否两两对得上（§4、§5）。

所有验收项编号 AV-xx，验证记录编号 VR-xx，供《需求分析质量验证报告》和最终验收测试引用。修改上游任何章节时，须同步更新本章对应条目。

## 1. 验收场景与验收表

### 1.1 验收口径

- **验收角色**：学生（STU）、管理员（ADM）、系统定时任务（Timer）三类；运维（OPS）仅涉及监控场景，不列入业务验收。
- **验收数据**：采用一套固定的模拟数据（2 个自习室、每室 30 个座位、3 个学生账号、1 个管理员账号），保证验收结果可复现。时间敏感场景（签到窗口、取消时限、自动违约）由测试人员通过调整数据库中预约单的时间字段构造，**不得修改服务器系统时间**（AS-03）。
- **判定标准**：每条验收项给出"通过条件"，全部子条件满足才判"通过"；任一子条件不满足判"不通过"并记录缺陷编号。
- **验收底线**（对应《用户需求》§2.1）：每个基本/期望功能必须满足"有数据留痕、状态流转正确、权限可拒绝"三点，验收表中以〔留痕〕〔状态〕〔权限〕标注。

### 1.4 验收执行说明

1. 执行顺序：先 AV-01（主闭环），再 AV-09～AV-12（预约类边界），然后 AV-03～AV-06（违约治理链），最后 AV-07、AV-08、AV-13～AV-16；违约治理链依赖前面场景产生的违约记录。
2. 每条验收项由执行人填写 §5 的验证记录（VR），"不通过"须附缺陷编号与截图/日志。
3. 涉及待确认问题（KQ-04、KQ-07、KQ-09 等）的验收项，在问题定稿前按"当前候选口径"执行并在记录中注明，定稿后复验。

- 每个脚本走查一遍即录一遍：记录人、日期、页面截图编号、发现的问题（缺口/文案不清/状态不可见）。

以下检查项由小组逐项核对并勾选，与《用户需求》§10 自查清单、《行为与状态》§4 的检查项互为补充：

- [ ] 原文 7 条与 FR 的对应（§2）经第二人复核签字。

### 4.3 缺陷与遗留问题的处理约定

1. 验收/走查发现的缺陷按"阻塞验收 / 影响体验 / 建议改进"三级归类，阻塞级缺陷清零后方可宣布验收通过。
2. 因 KQ 未定稿而挂起的验收项（AV-13 的已签到处置部分等）单独列表跟踪，定稿后 3 个工作日内完成复验。
3. 规则参数属可配置项（《规则与权限》§8.3），参数变更不视为需求变更，但须重跑受影响的 AV 项并更新 §4.2 的参数核对记录。
