# 质量要求

> 应能够查到的内容：重要的性能、可靠性、安全等要求及取舍理由
> 推荐表示形式：使用情境、指标和检验方法表
> 关键内容要求：质量要求应包含具体情境、可观察指标和检验方法；指标数值及取舍应给出依据或明确标记为待确认。

本章依据《项目概述》（成功指标、非目标）、《用户需求》（FR 清单、UC-01～UC-15、KQ 问题）与《规则与权限》（P/F/C 系列规则）编写，非功能需求统一编号 NFR-xx，供《验收与验证》章节的追踪矩阵引用。指标数值凡已有依据的注明出处，无法给出依据的一律标 **待确认** 并给出候选值与确认责任方。

## 0. 质量属性优先级与总体取舍

本系统是面向单一校区的课程级 Web 应用（非目标见《项目概述》§6.3），质量属性按以下优先级取舍：

| 优先级 | 质量属性 | 取舍理由 |
|---|---|---|
| 1 | 功能正确性 / 数据一致性 | 预约-违约-黑名单直接处分学生信用，任何"重复计违约""座位双占"都会造成真实权益损害，不可妥协 |
| 2 | 安全性（权限与个人信息） | 系统持有学号、违约记录等个人数据，涉众中的监管方明确关切（项目概述 §4）；但校园内网威胁模型有限，不按公网金融级设计 |
| 3 | 可靠性（定时任务与状态闭环） | 自动违约、黑名单解除依赖定时任务（AS-03），漏跑会产生错误处分；但不追求 99.99% 可用性，允许短时维护窗口 |
| 4 | 性能 | 校区量级（数千学生）并发有限，性能要求以保证"选课式瞬时高峰可用"为底线，不追求极限吞吐 |
| 5 | 易用性 | 学生高频使用，操作路径要短；但仅 Web 自适应页面，不投入原生 App |
| 6 | 可维护性 | 规则参数（15 分钟签到窗口等）须可配置（规则与权限 §8.3），其余按常规工程实践 |

总体取舍：**一致性、安全 > 峰值性能、极致体验**。理由：本系统错误代价（错误处分学生、座位冲突）高于延迟代价（慢 1 秒可接受）。

## 1. 性能要求（Performance）

### NFR-01 预约提交响应时间

| 项目 | 内容 |
|---|---|
| 使用情境 | 考试周晚间时段，学生查询到可用座位后点击"提交预约"（UC-01），系统需完成黑名单、时间窗、重叠、占用、并发共 6 项校验并写入预约单 |
| 可观察指标 | 从点击提交到页面返回预约单号的服务端处理时间；P95 ≤ 1 秒，P99 ≤ 2 秒 |
| 检验方法 | ① 压测脚本模拟峰值并发提交预约（并发数见 NFR-08），统计响应时间分位数；② UC-01 验收标准 ① 的手工计时复核 |
| 数值依据/取舍 | UC-01 验收标准已引用"1 秒内（指标待确认）"。取 1 秒是"用户不感知卡顿"的经验上限；预约属于强校验写操作，保证一致性（加锁）优先于极限速度。**峰值并发数待确认**（依赖 KQ 中预约频率口径） |

### NFR-02 座位查询与筛选响应

| 项目 | 内容 |
|---|---|
| 使用情境 | 学生按日期、时段、自习室、区域、属性标签筛选可用座位（FR-04/FR-07），座位可用性按 FR-05 实时计算 |
| 可观察指标 | 常规负载下筛选结果返回 P95 ≤ 2 秒；单自习室座位规模 ≤ 500 时，可用性计算不引起全表扫描恶化 |
| 检验方法 | 构造 500 座位 × 7 天 × 预约率 70% 的数据集，用接口压测统计分位数；核对返回的可用座位集合与手工按 FR-05 计算的结果一致（正确性优先于速度） |
| 数值依据/取舍 | 500 座位为单一校区单自习室规模的合理上界估计，**待确认**（依赖学校提供的场地规模）。筛选允许 2 秒慢于预约的 1 秒，因为查询不持锁、学生有等待预期 |

### NFR-03 数据分析页 10 秒自动刷新的性能代价

| 项目 | 内容 |
|---|---|
| 使用情境 | 管理员打开分析看板（FR-31～FR-33），页面每 10 秒自动刷新柱状图、折线图与统计数据（C-11，原文硬性要求） |
| 可观察指标 | ① 刷新后图表数据与数据库统计口径一致（C-8～C-10）；② 单次统计查询 P95 ≤ 2 秒，保证在 10 秒周期内完成；③ 多个管理员同时开看板时，刷新请求不显著拖慢学生端预约接口（预约接口 P95 劣化 ≤ 20%） |
| 检验方法 | ① 打开看板 60 秒，抓包确认每 10 秒 ± 1 秒一次请求；② 对比看板数值与 SQL 手工聚合结果；③ 压测中叠加看板刷新负载，观测预约接口分位数变化 |
| 数值依据/取舍 | 10 秒来自任务原文（不可改）。取舍：统计聚合**允许读取略有延迟的预聚合结果（延迟 ≤ 10 秒）而非每次实时聚合**，以保护交易库；因看板仅观测用，10 秒内数据滞后可接受。刷新导致页面滚动跳动、重复计数是不允许的（UC-08 验收点） |

## 2. 可靠性要求（Reliability）

### NFR-04 通知失败不阻断业务闭环

| 项目 | 内容 |
|---|---|
| 使用情境 | 投诉处理完成推送反馈通知、违约判定推送违约通知（FR-35）时通知服务异常（EX-13） |
| 可观察指标 | 通知推送失败时：① 业务状态（如投诉"已反馈"）仍正确落库；② 失败通知进入重试队列，24 小时内补发或记录死信告警；③ 业务接口返回时间不受通知失败影响（P95 仍满足 NFR-01） |
| 检验方法 | 测试环境模拟通知服务不可用，执行投诉反馈与违约判定用例，验证状态正确、通知重试日志存在；恢复服务后通知补达 |
| 数值依据/取舍 | 已被《行为与状态》EX-13 引用。取舍：通知采用"异步 + 重试"，放弃"通知与业务强一致"，因为通知延迟不损害权益，强一致会放大故障面 |

### NFR-05 定时任务的幂等与可恢复性

| 项目 | 内容 |
|---|---|
| 使用情境 | 自动违约判定、黑名单加入/期满解除的定时任务（UC-03/UC-06/UC-14，AS-03）因进程重启、异常中断而漏跑或重复执行 |
| 可观察指标 | ① 同一预约单被多个扫描周期命中只产生 1 条违约记录（幂等）；② 任务中断后补跑，漏判数据在下一周期全部补齐且不重复；③ 任务连续失败 ≥ 3 次触发告警（告警渠道**待确认**，候选：日志 + 运维看板）；④ 黑名单解除以"当前时间 > 结束时间"实时判断兜底，不依赖状态字段被刷新（ST-14a） |
| 检验方法 | ① 手工将任务重复触发两次，核对违约/黑名单记录条数；② 在任务执行中 kill 进程后重启，核对补跑结果；③ 校验 UC-03 验收标准 ④、UC-06 验收标准 ⑤ |
| 数值依据/取舍 | 幂等条件已定稿于用例验收标准；扫描周期候选 1 分钟（KQ-06 **待确认**）。取舍：扫描周期越短违约释放越及时，但数据库扫描开销越大；1 分钟对"15 分钟签到窗口"的判定精度足够（误差 ≤ 1/15） |

### NFR-06 敏感操作留痕的完整性

| 项目 | 内容 |
|---|---|
| 使用情境 | 管理员执行手动违约登记、投诉处理、黑名单加入/解除、代约、删除违规评价（FR-20、BR-12、F-10） |
| 可观察指标 | ① 每次敏感操作产生 1 条审计日志，含操作人、时间、对象、原因，不可被删除（F-10）；② 审计日志与业务记录一一对应，抽检 100 条无缺失；③ 越权尝试（UC-11）同样写入日志 |
| 检验方法 | 自动化测试对每类敏感操作断言日志新增；对审计表尝试 DELETE 应被拒绝；按 UC-04 验收标准 ④ 验证学生调用管理接口有日志 |
| 数值依据/取舍 | FR-20/NFR-06 引用关系已在需求清单建立。取舍：日志只增不改会带来存储增长，但敏感操作本身低频（UC-04/UC-06 均低频），单学期量级可忽略，故不做归档策略（**若长期运行需补充归档方案，待确认**） |

## 3. 安全性要求（Security）

### NFR-07 权限的服务端强制校验

| 项目 | 内容 |
|---|---|
| 使用情境 | 学生构造请求直接调用管理员接口（手动违约登记、黑名单管理），或学生 A 请求查看/取消学生 B 的预约（F-3、F-7、UC-11） |
| 可观察指标 | ① 未授权请求 100% 返回 403，且不产生任何业务数据变更；② 权限校验在服务端完成，绕过页面（直接发 HTTP 请求）同样被拒；③ 学生查询他人数据（他人预约 id、他人投诉）返回 403 或空列表，错误信息不泄露他人字段；④ 运维角色访问业务明细数据被拒（F-9） |
| 检验方法 | 用接口工具（curl/Postman）持学生令牌调用全部管理端接口逐一验证；遍历 ID 尝试越权读取（IDOR 测试）；核对 UC-11 验收点与审计日志 |
| 数值依据/取舍 | 100% 拦截是安全类指标的硬性要求，无取舍空间；页面隐藏按钮仅作为体验层，不作为安全手段（已在 UC-11 明确） |

### NFR-08 个人信息保护

| 项目 | 内容 |
|---|---|
| 使用情境 | 系统存储学号、姓名、违约记录、投诉内容等个人信息；座位看板对全体学生可见（5.1：实时状态全局可见但**不含占用者身份**） |
| 可观察指标 | ① 学生端任何接口不返回他人姓名/学号/违约信息，座位仅显示"已占用"；② 口令不以明文存储（加盐哈希），数据库泄露不可直接还原口令；③ 运维监控视图仅展示脱敏量级统计（F-9、P-12）；④ 审计日志中的个人信息访问可追溯 |
| 检验方法 | 抓包学生端全部接口响应，检查字段白名单；检查数据库口令字段格式；以运维账号尝试查询任一学生明细应被拒 |
| 数值依据/取舍 | "座位对他人匿名"取自《规则与权限》5.1 已定稿口径。取舍：不接统一身份认证（非目标 §6.3-3），自建账号体系降低了集成复杂度，但需自行承担口令存储安全（哈希为最低要求）；是否满足《个人信息保护法》告知同意义务**待确认**（监管方关切，责任方：学校管理部门） |

### NFR-09 输入校验与注入防护

| 项目 | 内容 |
|---|---|
| 使用情境 | 学生在投诉内容、评价文字、违约原因等自由文本字段提交恶意内容（SQL 注入、XSS、超长文本）；评分字段提交越界值 |
| 可观察指标 | ① 所有自由文本长度受限（投诉 ≤ 500 字，候选值**待确认**）；② 注入攻击载荷被原样存储或拒绝、不执行；③ 评分超出 1～5 被拒（UC-09 验收标准 ③）；④ 全空白内容被拒（UC-05 异常 2a） |
| 检验方法 | 对文本字段注入典型 SQL/XSS 载荷回归验证；边界值测试（空串、空白、超长、评分 0/6） |
| 数值依据/取舍 | 常规 Web 安全底线，无取舍。评价内容的辱骂拦截"关键词提示"为候选（KQ 相关待确认），自动拦截不做硬性要求，删除权留给管理员（BR-17） |

## 4. 易用性要求（Usability）

### NFR-10 核心操作路径长度

| 项目 | 内容 |
|---|---|
| 使用情境 | 学生完成一次预约（US-02"一步完成预约"）、在窗口内签到（US-04"入口自动出现并可一键签到"）、签退后顺带评价（US-11） |
| 可观察指标 | ① 登录状态下：预约 ≤ 3 次点击（选时段→选座位→确认）；② 签到窗口外按钮置灰并显示开放时间，窗口内一键签到 ≤ 2 次点击；③ 所有拒绝类操作返回含规则原因的提示（规则与权限 §8.1：须返回规则编号或原因） |
| 检验方法 | 原型走查/可用性测试：邀请 5 名学生完成预约、签到、取消三项任务，记录点击数与出错次数，任务完成率 ≥ 90%，无需求助 |
| 数值依据/取舍 | 点击数上限直接来自 US-02/US-04 的用户故事承诺；5 人小样本走查为课程项目可行的检验规模（Nielsen 可用性测试经验最小样本） |

### NFR-11 关键状态反馈及时性

| 项目 | 内容 |
|---|---|
| 使用情境 | 取消预约、签退后座位释放，其他学生应能看到新空位（BR-09"即时释放"）；管理员登记违约后看板立即变"空闲"（UC-04 验收 ⑤） |
| 可观察指标 | 释放类操作完成后，其他会话 ≤ 10 秒内可查询到该时段可约（与分析刷新共用 10 秒口径；实时看板刷新周期随 KQ-06 **待确认**，候选 10 秒） |
| 检验方法 | 双浏览器会话：A 取消/签退，B 立即查询该座位时段，记录从操作到 B 可见的延迟，重复 10 次取最大值 |
| 数值依据/取舍 | "即时释放"指数据层即时（事务提交即释放），展示层允许 ≤ 10 秒延迟。取舍：不做 WebSocket 推送、用轮询/查询刷新，实现简单且与分析页刷新周期一致 |

## 5. 可维护性与可配置性要求（Maintainability）

### NFR-12 业务规则参数可配置

| 项目 | 内容 |
|---|---|
| 使用情境 | 学校管理部门在评审后调整签到窗口（15 分钟）、取消时限（30 分钟）、预约窗口（7 天）、违约阈值（3 分）、限制期（7 天 × 次数，上限 30 天）等参数（规则与权限 §8.3） |
| 可观察指标 | ① 上述参数存于配置表/配置项，修改后**无需改代码重新部署**即生效；② 参数调整写入变更留痕（UC-06 异常 2b）；③ 代码中不出现这些魔法数字的硬编码 |
| 检验方法 | 测试环境修改配置（如签到窗口 15→20 分钟），验证 UC-03 判定边界随之变化；代码评审检查无硬编码 |
| 数值依据/取舍 | 规则与权限 §8.3 已定稿要求可调整。取舍：配置化增加少量读取开销，但规则属"学校政策"而非"技术常量"，变更概率高，必须配置化 |

## 6. 数据质量与一致性要求

### NFR-13 座位时段唯一性与并发正确性

| 项目 | 内容 |
|---|---|
| 使用情境 | 两名学生在同一毫秒对同一座位同一时段提交预约（UC-13）；高峰期大量并发写预约表 |
| 可观察指标 | ① 数据库层面同一座位同一时段至多 1 条有效预约（唯一约束或等价锁机制，BR-04）；② 并发提交仅一方成功，失败方收到明确提示；③ 并发压测（候选 50 并发争抢同一时段，数值**待确认**）100 次无一双占 |
| 检验方法 | 并发脚本对同一座位同时刻发起 N 个预约请求，断言成功数 = 1；检查数据库约束存在；核对 UC-13 验收点 |
| 数值依据/取舍 | 一致性 > 吞吐：宁可排队或拒绝，不允许双占。50 并发为单座位争抢的极端上界假设（远超真实人数），**待确认** |
